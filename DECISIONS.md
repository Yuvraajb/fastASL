# fastASL — decisions log

Decisions made while building, in the order they came up. Each entry: what, why, and what it costs.

## Setup

1. **Branch `krishna`, never `main`.** The GitHub repo was empty (no commits, no `main` yet), so `krishna` starts from an empty history.
2. **Toolchain pinned for Node 20.19.** The machine has Node 20.19.4. Electron 40+ and Vitest 5 declare `node >= 22.12`, so we pin **Electron 39**, **Vite 7**, **electron-vite 6**, **Vitest 3**, **TypeScript 5.9**. Everything else is current (React 19, lucide-react, @mediapipe/tasks-vision 1.1.1, @anthropic-ai/sdk 1.x). Upgrading to Electron 45 later is a version bump once the team is on Node 22.
3. **zod 3, not 4.** `@factory/droid-sdk` has a peer dependency on `zod@^3.24` and converts tool schemas with zod-to-json-schema, so the whole app uses zod 3.25.
4. **electron-vite** builds main / preload / renderer. `npm run dev` gives HMR for the renderer.

## Window & visuals

5. **CSS glass by default; native vibrancy is opt-in (`FASTASL_VIBRANCY=hud`).** Electron masks the NSVisualEffectView of a frameless window with a hard-coded 9pt corner radius and exposes no option to change it (verified in Electron source/docs, see `docs/research/platform-research.md`). The reference images and brief call for 22px corners, and a 9pt blur rectangle behind a 22px card leaves visible blurred wedges in each corner. So the default window is `transparent: true` with a dark translucent CSS card (exact 22px radius, 1px hairline border, native window shadow recomputed with `invalidateShadow()` after each resize). Setting `FASTASL_VIBRANCY=hud` (or `popover`) turns on real `vibrancy` + `visualEffectState: 'active'`; the card then uses a more transparent background and the system corner radius. Native custom-radius blur would need a native addon (e.g. the unofficial `electron-liquid-glass` for macOS 26), which we judged too risky for a hackathon build.
6. **`type: 'panel'` + `focusable: false` + `showInactive()`.** An NSPanel floats over full-screen apps and never steals focus, which matters because Dictation types into whatever app is focused. The window becomes focusable only while the user edits text with the keyboard (sentence pencil, stream URL), then goes back.
7. **The window is always exactly the card.** The renderer measures the card (ResizeObserver) and sends its size; the main process animates bounds with a critically damped spring (~200ms settle) at 60Hz, right edge pinned, 12px below the menu bar and 12px from the right edge. `prefers-reduced-motion` (macOS "Reduce motion") snaps instantly.
8. **Dev tooling.** Dev mode (`npm run dev`, or `FASTASL_DEV=1`) registers global hotkeys: **Option+1…9** jump to the nine states in reference image 3 (Ready, Recognizing, Building, Sentence, Agent ready, Working, Confirm, Done, Collapsed); **Option+0** toggles the in-card dev panel (every mock state, gesture simulator, FPS); **Control+Option+key** simulates gestures (T thumbs up, F fist, ←/→/↑ swipes, 1–5 fingers, P palm hold, H hands down, S next recognized sign, V peace sign). A menu-bar tray item ("ASL") has Show/Hide, Quit and (dev) the same state/gesture menus. These are global shortcuts because the overlay never has keyboard focus.
9. **Screenshots.** `npm run screens [ids]` builds into a temp dir and opens an opaque "stage" window (fake menu bar + dusk wallpaper, card top-right with CSS backdrop blur), applies each mock scene, and saves `docs/screens/NN-<id>.png` via `webContents.capturePage()`. Reference images live in `docs/reference/` with per-state zoomed crops in `docs/reference/crops/`.

## Architecture

10. **One controller owns every state change** (`src/renderer/src/app/controller.ts`). Gestures, mouse taps, recognition events and agent events all go through it; it gates gestures per state (`activeGestures`) and talks to the outside world through a `Services` interface (mock implementation for UI work/screenshots, IPC implementation for real use).
11. **High-frequency data stays out of React.** Camera frames, landmarks and hand-motion energy live in a mutable `live` object read by canvases inside `requestAnimationFrame`.
12. **More than three numbered options.** Menus with 4–5 entries (Settings, Quick menu) accept **4 fingers** (thumb folded) and **5 = open palm held 0.8s**. Open-palm-to-expand only applies in the Collapsed state, so the two never collide.

## Phase 1 — UI

13. **Design system in `src/renderer/src/ui/`** (documented in `ui/README.md`): Header, StatusLabel, Feed (+ pure `feedDraw.ts` used for both the mock hand and real landmarks), TokenPill, TokenStrip, QuoteBox, ActivityBars, IconButton, Footer, Button/ButtonRow, StepsList, OptionList, CheckBadge, HoldRing, Notice, CloseButton, Spinner, ProgressLine, Stack, Hint. Views compose only these, so every state shares one spacing/type scale.
14. **Mock hand instead of a blank feed.** With no camera (Phase 1, screenshots, camera off/denied) the feed draws a shaded grayscale hand for a pose that fits the state (palm, fist "A", "C", thumbs up, point, OK, peace, two hands) with real 21-point MediaPipe landmarks on top. It reads as an illustration rather than a photo; the live camera replaces it.
15. **Collapsed pill follows ref 2** (round live thumbnail + green dot + "fastASL" + chevron) rather than ref 3's camera-icon variant, as the brief specifies. The palm-hold progress ring wraps the thumbnail.
16. **Feed aspect varies slightly by state** (16:10 by default, taller in Ready/Recognizing like ref 3, shorter in Agent ready/Settings) to match the references' proportions while keeping the 300/340px widths.
17. **Gesture hints are tiny gray lucide icons + words** ("👍 send · ✊ cancel" without emoji color), so the palette stays monochrome (green dot/check and the red dictation dot are the only colors).
18. **Controller hardening from the test pass** (102 vitest tests in `app/controller.test.ts`): late agent events after Stop are ignored (late confirms are auto-declined), a Stop before the agent starts prevents the run, "thinking" can't get stuck or be overwritten by a stale answer, and failed results stay up 8s (matching their progress line) instead of 4s.

## Phase 2 — Camera

19. **`app/engines.ts` is the single owner of the camera pipeline** (and, from Phase 3, the gesture and recognition engines). App starts it once the saved settings are loaded, but never in screenshot / stage mode or with `?mock=1`, so screenshots always show the mock hand. Camera settings reach it through the store, not through direct calls: `controller.toggleCamera()` sets `cameraOn` and the new `controller.setCameraSource()` sets `cameraSource` (used by the finger pick and the URL field); engines.ts subscribes to both and calls `setEnabled` / `setSource`. That way the controller never imports the engine (no import cycle once the gesture engine calls back into the controller), and the store stays the renderer's one copy of the settings. `subscribeFrames(fn)` fans every tracked frame out to later phases; an empty frame is sent whenever the camera goes away so no consumer holds stale hands.
20. **MediaPipe assets are bundled locally, SIMD build only.** `scripts/fetch-assets.mjs` (run by `postinstall` and `npm run setup`) copies `vision_wasm_internal.{js,wasm}` from `@mediapipe/tasks-vision` and downloads the pinned `float16/1` `hand_landmarker.task` (7.8 MB, MD5 checked against Google Cloud Storage's `x-goog-hash`, written via `.part` + rename). Skipping the non-SIMD build saves ~26 MB; Electron always has SIMD. The ~21 MB of generated files live in `src/renderer/public/mediapipe/` (gitignored) and electron-vite copies them to `out/renderer/mediapipe`. They resolve relative to `location.href`, which works from both the dev server (http) and the built app (file://) under the existing CSP, so the `assetBase` IPC / `fastasl-asset:` scheme stay unused. MediaPipe's telemetry POST to `odml.pa.googleapis.com` is blocked by the CSP; it only logs a console error, and we leave it blocked. Loading from inside `app.asar` (a packaged build) is untested.
21. **ESP32-CAM streams go through a local CORS proxy** (`src/main/camera/mjpegProxy.ts`), started in `boot()` (not in screenshot mode) and closed on `will-quit`. Embedded cameras never send `Access-Control-Allow-Origin`, and without it the `<img>` taints the canvas and MediaPipe can't read it. The proxy binds 127.0.0.1 on a random port and every URL carries a per-launch token (403 without it), because a CORS-open local relay could otherwise be used by any web page to read LAN devices. If the proxy fails to start, only MJPEG sources fail ("Can't reach the ESP32 stream"); the built-in camera still works.
22. **One 5s timeout, passed as the `timeout` request option, covers connecting and stalls.** The option arms the socket idle timer before DNS + TCP connect; `req.setTimeout()` only arms after `'connect'`, which left an unplugged ESP32 or a wrong IP hanging ~75s. The same timer ends a stream that stops sending (a Wi-Fi drop leaves the socket open). The renderer's 8s limit is a backstop.
23. **The renderer asks the proxy with `fetch()` before loading the `<img>`**, because an `<img>` can't read error text: this gives specific messages (camera unreachable / URL is a web page, not a stream / unsupported scheme) without waiting for two timeouts. A stream that breaks off is detected by the image going blank (`naturalWidth` 0, Chrome fires no `error` on a broken multipart `<img>`) and reported as "Lost the ESP32 stream".
24. **The proxy hangs up on the camera when the renderer leaves, and each stream gets its own socket (`agent: false`)**, because ESP32 firmware serves one stream client at a time. Verified in the smoke test: switching source or turning the camera off makes the mock camera log "client left" immediately.
25. **For MJPEG the canvas is the single frame source.** Each animation frame copies the `<img>` into a canvas that MediaPipe and the Feed both read (never tainted, resizes with the stream). Known trade-off: `<img>` has no per-frame event, so a 15 fps ESP32 stream gets ~30 detections/s (each frame processed twice, ~10 ms each on the main thread). The fix, if needed, is to `fetch()` the stream, split the parts and use `createImageBitmap`.
26. **The built-in camera's `deviceId` is `ideal`, not `exact`**: if the chosen camera is unplugged, any camera beats none for this audience. Video frames are scheduled with `requestVideoFrameCallback` (fires 30/s even on a `<video>` that is not in the page), the MJPEG canvas with `requestAnimationFrame`.
27. **Hand tracking: GPU first, CPU fallback, ~30 detections/s.** `HandLandmarker` runs in VIDEO mode with 2 hands; detection confidence 0.6 (fewer false hands), presence and tracking 0.5 (sticky). One warm-up inference on a blank `ImageData` at load time catches GPU failures early enough to fall back to CPU and moves shader compilation off the first camera frame. Timestamps are forced to increase (MediaPipe rejects equal or earlier ones). Detections are throttled to one per 26 ms: ~29 ms lost frames to jitter (22 detections/s on a 30 fps camera), 26 ms measured 28.5/s and still caps 60/120 Hz displays at ~30/s.
28. **Pipeline recovery.** A session counter makes stale async work discard itself; the tracker is shared across sources and rebuilt after an inference error. Failures fall back to the mock hand with `live.error` set and retry with backoff (1s doubling to 10s, reset once frames actually flow), except missing MediaPipe files (33). Only a backoff retry of the same source keeps the last error visible (no flicker); `start()`, a real source change and turning the camera back on clear the error and reset the backoff, so an old source's error never shows while a new one opens.
29. **Motion energy (drives the activity bars) is measured in hand sizes per second**: hand size is the larger of wrist→middle knuckle and index→pinky knuckle, so it doesn't depend on distance to the camera; hands are paired between frames by nearest wrist (handedness labels flicker); x is corrected for aspect; speeds under 0.3 hand sizes/s are jitter, the rest goes through tanh(speed/3) and a 150 ms time constant, so 15 and 30 fps behave the same.
30. **The macOS camera prompt is only requested when the built-in camera will be used** (saved source is built-in and the camera is enabled). An ESP32-only setup never sees a camera prompt. Switching to the built-in camera later relies on `getUserMedia` to raise the prompt (not verified, to avoid permission prompts while testing); if it doesn't, the next launch asks at boot because the saved source is now built-in.
31. **Dev diagnostics.** In dev the full feed shows a tiny gray tabular "30 fps" top-right while the live camera runs (hidden with the mock hand, so screenshots are unchanged), and engines.ts logs a `[camera] live 640x480 · 30 fps · 1 hand(s)` line whenever that status line changes (checked every 2s). `FASTASL_LOG=1` forwards the renderer console to the main process's stdout and `FASTASL_DATA_DIR=<dir>` overrides the data directory, so a smoke test can launch the built app with its own `settings.json` and read the camera status from the terminal.
32. **`npm run mock:mjpeg` stands in for an ESP32-CAM** at `http://127.0.0.1:8081/stream` (`multipart/x-mixed-replace;boundary=frame`, plus `/capture`), fed by ffmpeg from the Mac camera or, with `--test`, a 15 fps test pattern that needs no camera permission. It runs ffmpeg continuously, binds 127.0.0.1 and drops frames for slow clients the way a real camera does. Requires `brew install ffmpeg`; no new npm dependencies.
33. **The tracker loads before the camera opens, and missing MediaPipe files are a permanent, readable error.** Opening both in parallel saved a few hundred ms on the first launch, but a tracker that can't load then opened and closed the camera on every retry (the green light blinking forever, an ESP32 reconnect each time). Now the tracker comes first (it is cached, so later restarts don't wait for it). Before loading, `createHandTracker` fetches the wasm loader, the wasm binary and the model (local files, the body is cancelled) and throws `MissingAssetsError` if any is missing: on file:// a missing file rejects, and the dev server answers with its `index.html` (200, `text/html`), so HTML counts as missing. The card shows "Hand tracking files are missing — run npm run setup" (like "Add <KEY> to .env") and the pipeline stops retrying, since the files won't appear by themselves; a relaunch, the camera toggle or a new source tries again. Covers a failed `postinstall` (offline, firewall), `npm ci --ignore-scripts` and a deleted `public/mediapipe`. Any other load failure that rejects with a DOM `Event` (a `<script>` that didn't load) becomes "Hand tracking failed to load (the MediaPipe runtime script failed to load)" instead of "[object Event]", and still retries with backoff without touching the camera.
34. **`store.getSettings()` validates the camera source.** Main (`boot()` reads it for the camera prompt) and the renderer (through IPC) both read settings there, so one check covers both. Anything other than `{kind:'builtin', deviceId?: string}` or `{kind:'mjpeg', url: string}` falls back to the built-in camera. Before, a hand-edited `"cameraSource": null` threw inside `boot()` after the dock icon was hidden, leaving the app running with no window and no tray icon.

## Phase 3 — Gesture engine

35. **`GestureEngine` (`src/renderer/src/engine/gestures/`) is pure and deterministic; `app/gestureInput.ts` connects it to the app.** `connectGestures(controller, subscribeFrames)` feeds it every frame from the camera pipeline (frames with no hands included), sends each fired gesture to `controller.gesture()` (which gates by view a second time), and on every view change calls `setActive(activeGestures(view))` (via `useApp.subscribe`), so the engine only evaluates, fires and shows progress for gestures the current view accepts. The sensitivity setting maps to `SENSITIVITY[s]` (hold times × `holdScale`, swipe distance/speed × `swipeScale`) and applies immediately. `startEngines(controller)` now takes the controller from App instead of importing the singleton, so `engines.test.ts` drives the real wiring (synthetic frames → engine → real `Controller` on mock services → store) without `context.ts`'s `location`-based service pick. The engine costs a few µs per hand per frame, so it stays on the renderer's main thread. No new dependencies.
36. **Hold progress goes to the store only when it changes.** `holdProgress` fills the collapsed pill's ring and `pick` the option badge's ring; both are compared with the store before each write, so idle frames cause no React renders (a hold renders at camera rate, ~30/s, for its 0.5–1 s). While the live camera runs the engine owns both fields: a dev scene's mock ring (the tray's "Collapsed + palm hold" scene, the quick menu's pick) disappears on the next frame. Screenshots and `?mock=1` never start the engines, so they keep the scene values. Dev-simulated gestures (Ctrl+Opt hotkeys, dev panel) still call `controller.gesture()` directly and bypass the engine. The engine's custom-shape progress (`progress().shape`) has no store field yet.
37. **A new camera session starts the engine from scratch.** Every camera session (new source, restart after a failure, camera turned back on) opens a new `<video>`/`<canvas>`, so a change of `live.source`, or of the frame's aspect ratio (an ESP32 can change resolution mid-stream), triggers `setAspect(width / height)` and `reset()`: no tracks, holds, cooldowns or armed hands-down carry over (otherwise a phrase could end the instant the camera came back after hands had gone down). Frames that arrive while `live.mock` is set are not real hands and are skipped; the pipeline sends one such empty frame when the camera goes away, which clears any half-filled ring. A store subscription on `cameraSource` was rejected because a failure retry changes no setting and the new source's size is only known once frames flow. Cost: spent holds are forgotten too, so fingers still held while Settings › Camera source switches the camera pick the same row again once the new feed appears, which re-selects the source that is already active (no restart).
38. **Swipe direction follows the mirrored preview.** MediaPipe landmarks are raw camera coordinates, but the feed is drawn mirrored, so a hand moving toward the left of the preview (the user's own left) moves +x in the raw frame. Raw +x is reported as `swipeLeft` (previous mode in Ready/Dictation, delete last word while building and in Sentence, previous teach page), raw −x as `swipeRight` (next mode, proceed). The direction does not depend on the Left/Right handedness label. Checked end to end: an MJPEG stream of a hand photo sliding +x fired `swipeLeft in ready` and the mode went command → spell; sliding −x fired `swipeRight` (spell → command).
39. **Geometry is aspect-corrected.** Landmark x and z are multiplied by width/height before any shape or speed math; without it a 16:9 frame squashes sideways shapes by 1.78×. Swipe distances are still measured in frame widths and heights.
40. **Shape rules return nothing when unsure.** A finger counts as extended when the average of two signals (bend between proximal and distal phalanges; fingertip-to-wrist over PIP-to-wrist distance) is ≥ 0.7, folded at ≤ 0.3, "partial" in between, so relaxed and C hands never trigger controls. The thumb uses chord ÷ path straightness (its short segments make joint angles jittery), capped by its reach from the index knuckle. Open palm uses |palm facing| (handedness labels are unreliable). Counts 2 and 4 need a folded thumb, 1–4 an upright hand, 5 an open palm. ASL A falls in a deliberate gap between fist and thumbs-up (fewer false cancels while fingerspelling); a thumbs-down reads as a fist ("no" either way). Priority when a hand matches several: thumbs up > fist > palm hold > fingers > custom shape > built-in peace, among active gestures only.
41. **Holds: 1.0 s palm, 0.8 s fingers and shapes, 0.9 s fist, 0.5 s thumbs up** (the strictest shape test, so it can be shorter), times × `holdScale`. Timing starts at the first frame of the stable run; 1–2 frames of a different reading or a dropped hand don't reset it, the third does. Every visible hand must be still (wrist < 0.8 palm lengths/s over 200 ms), so a passive base hand under a moving dominant hand never completes a fist, and a hold never fires on a moving frame. Signs change handshape every ~150–400 ms, well under any hold.
42. **Release and cooldowns.** After any event the engine is silent for 700 ms, and the same gesture and parameter (`fingers:2`, `shape:<id>`) can't refire for 1.5 s. A fired hold must also be released before it can start again, even across view changes: no hand may show it for 300 ms (`RELEASE_MS`). The release is timed rather than counted in frames. At first, 3 frames without the gesture counted as letting go, so a 100 ms tracking dropout or a short misread re-armed a thumbs-up that was still up. It then refired once the 1.5 s cooldown ended, and by then the view had moved on: a thumbs-up kept up in Sentence proceeded and then started the agent, and one kept up in Agent ready then approved the confirm step. 300 ms is longer than a dropout and shorter than any deliberate release, which is followed by a 0.5–1 s hold anyway. Holding a fist after it cancels the quick menu therefore does not also collapse Ready. A hold blocked by a cooldown fires as soon as the cooldown clears.
43. **Swipes need a long, fast, straight stroke by a flat hand while other hands rest:** ≥ 0.22 frame widths (≥ 0.20 heights up) within 300 ms, peak speed ≥ 1.2 widths/s (over ≥ 60 ms, see 48), main axis > 2.2× the cross axis, the hand flat in at least half the window. Guards against signing and accidents: only motion after the hand was first seen at rest (≥ 100 ms) counts, so raising a hand into view is not a swipe; each stroke is decided once (fired or discarded) and the rest of its motion is ignored until the hands rest; the opposite swipe is ignored until 1.2 s after the swipe's motion ends (return stroke); a swipe that interrupts a hold at least 60% done is discarded; and the shapes the swiping hand showed are spent, so holding the open hand still after a swipe in Settings doesn't pick option 5. Hands are matched across frames by wrist position, globally and closest first, so a second hand appearing next to a held one can't take over its track (which would read as a jump and a swipe).
44. **Both hands down arms only after 3 frames with hands and fires once** (1.2 s × `holdScale` after the last hand), then waits for hands to return. Entering a view that accepts it with the hands already down does not fire it.
45. **The built-in peace sign is reported as shape `builtin-peace`** and reaches `controller.runShortcut` in Ready and Collapsed (mock services until Phase 5, so it only shows the toast). `GestureEngine.setShapeMatcher` for custom gestures is not wired yet: the "New gesture" capture flow comes in a later phase. The matcher keeps running while a custom shape is spent, so a shape held through its toast won't fire twice.
46. **Dev diagnostics.** In dev every fired gesture logs `[gesture] <gesture[:param]> in <view>` (the view it fired in, before the controller acts); with `FASTASL_LOG=1` it reaches stdout next to the `[camera]` line.
47. **Every new view needs a fresh gesture.** When the view kind changes, `gestureInput` calls `engine.spendShown()`, which marks every gesture shown at that moment, or within the last 300 ms (a dropout just at the change), as spent. A thumbs-up raised while the agent works therefore can't approve the confirm step that appears under it, and a hold in progress restarts from zero in the new view. It runs only on a change of kind, not on every view update, because the Working card is replaced on each agent step: spending there would keep a held stop-fist from ever completing. Settings pages share one kind, so moving between them doesn't spend anything. Fingers picks are spent when they fire, so this needs no extra rule.
48. **Swipe peak speed is measured over at least 60 ms (`SWIPE.speedSpanMs`), not frame to frame.** The pipeline tracks an MJPEG canvas on every animation frame (~30/s) whatever the stream's own rate, so a 15 fps ESP32 or `npm run mock:mjpeg` stream reaches the engine with each image twice, 33 ms apart. The FPS readout then shows about 30, the detection rate. Frame to frame, the speed read 0 and then twice the real speed, so a steady 1 frame width/s reposition passed the 1.2 widths/s gate and swiped (proceed or delete a word in Sentence). It was rejected on a 30 fps camera. Measured from the latest sample at least 60 ms earlier, a repeated image counts as one 66 ms step, and the same span also absorbs frames that arrive bunched or late. On a 30 fps camera that span is two frames, which lowers a real swipe's peak by about 3%. Skipping repeated images in the pipeline (comparing a thumbnail of each canvas) was rejected for now: a static test stream would then stop producing frames, and it would change Phase 2 code that has no DOM tests. Only the swipe speed depends on the sample spacing; holds, release and hands-down are timed, and the flicker tolerance of 2 frames shrinks to ~66 ms on such a stream, the same as on a 30 fps camera.
