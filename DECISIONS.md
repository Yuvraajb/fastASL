# fastASL — decisions log

Decisions made while building, in the order they came up. Each entry: what, why, and what it costs.

## Setup

1. **Branch `krishna`, never `main`.** The GitHub repo was empty (no commits, no `main` yet), so `krishna` starts from an empty history.
2. **Toolchain pinned for Node 20.19.** The machine has Node 20.19.4. Electron 40+ and Vitest 5 declare `node >= 22.12`, so we pin **Electron 39**, **Vite 7**, **electron-vite 6**, **Vitest 3**, **TypeScript 5.9**. Everything else is current (React 19, lucide-react, @mediapipe/tasks-vision 1.1.1, @anthropic-ai/sdk 1.x). Upgrading to Electron 45 later is a version bump once the team is on Node 22.
3. **zod 3, not 4.** `@factory/droid-sdk` has a peer dependency on `zod@^3.24` and converts tool schemas with zod-to-json-schema, so the whole app uses zod 3.25.
4. **electron-vite** builds main / preload / renderer. `npm run dev` gives HMR for the renderer.

## Window & visuals

5. **CSS glass by default; native vibrancy is opt-in (`FASTASL_VIBRANCY=hud`).** Electron masks the NSVisualEffectView of a frameless window with a hard-coded 9pt corner radius and exposes no option to change it (verified in Electron source/docs, see `docs/research/platform-research.md`). The reference images and brief call for 22px corners, and a 9pt blur rectangle behind a 22px card leaves visible blurred wedges in each corner. So the default window is `transparent: true` with a dark translucent CSS card (exact 22px radius, 1px hairline border, native window shadow recomputed with `invalidateShadow()` after each resize). Setting `FASTASL_VIBRANCY=hud` (or `popover`) turns on real `vibrancy` + `visualEffectState: 'active'`; the card then uses a more transparent background and the system corner radius. Native custom-radius blur would need a native addon (e.g. the unofficial `electron-liquid-glass` for macOS 26), which we judged too risky for a hackathon build.
6. **`type: 'panel'` + `focusable: false` + `showInactive()`.** An NSPanel floats over full-screen apps and never steals focus, which matters because Dictation types into whatever app is focused. The window becomes focusable only while the user edits text with the keyboard (sentence pencil, stream URL), then goes back. On macOS `setFocusable(false)` alone leaves the panel with the keyboard, so since Phase 7 it also hands the keyboard back (97).
7. **The window is always exactly the card.** The renderer measures the card (ResizeObserver) and sends its size; the main process animates bounds with a critically damped spring (~200ms settle) at 60Hz, right edge pinned, 12px below the menu bar and 12px from the right edge. `prefers-reduced-motion` (macOS "Reduce motion") snaps instantly.
8. **Dev tooling.** Dev mode (`npm run dev`, or `FASTASL_DEV=1`) registers global hotkeys: **Option+1…9** jump to the nine states in reference image 3 (Ready, Recognizing, Building, Sentence, Agent ready, Working, Confirm, Done, Collapsed); **Option+0** toggles the in-card dev panel (every mock state, gesture simulator, FPS); **Control+Option+key** simulates gestures (T thumbs up, F fist, ←/→/↑ swipes, 1–5 fingers, P palm hold, H hands down, S next recognized sign, V peace sign). A menu-bar tray item ("ASL") has Show/Hide, Quit and (dev) the same state/gesture menus. These are global shortcuts because the overlay never has keyboard focus.
9. **Screenshots.** `npm run screens [ids]` builds into a temp dir and opens an opaque "stage" window (fake menu bar + dusk wallpaper, card top-right with CSS backdrop blur), applies each mock scene, and saves `docs/screens/NN-<id>.png` via `webContents.capturePage()`. Reference images live in `docs/reference/` with per-state zoomed crops in `docs/reference/crops/`.

## Architecture

10. **One controller owns every state change** (`src/renderer/src/app/controller.ts`). Gestures, mouse taps, recognition events and agent events all go through it; it gates gestures per state (`activeGestures`) and talks to the outside world through a `Services` interface (mock implementation for UI work/screenshots, IPC implementation for real use).
11. **High-frequency data stays out of React.** Camera frames, landmarks and hand-motion energy live in a mutable `live` object read by canvases inside `requestAnimationFrame`.
12. **More than three numbered options.** Menus with 4–5 entries (Settings, Quick menu) accept **4 fingers** (thumb folded) and **5 = open palm held 0.8s**. Open-palm-to-expand only applies in the Collapsed state, so the two never collide.

## Phase 1 — UI

13. **Design system in `src/renderer/src/ui/`** (documented in `ui/README.md`): Header, StatusLabel, Feed (+ pure `feedDraw.ts` used for both the mock hand and real landmarks), TokenPill, TokenStrip, QuoteBox, ActivityBars, IconButton, Footer, Button/ButtonRow, StepsList, OptionList, CheckBadge, HoldRing, Notice, CloseButton, Spinner, ProgressLine, Stack, Hint. Views compose only these, so every state shares one spacing/type scale.
14. **Mock hand instead of a blank feed.** With no camera (Phase 1, screenshots, camera off/denied) the feed draws a shaded grayscale hand for a pose that fits the state (palm, fist "A", "C", thumbs up, point, OK, peace, two hands) with real 21-point MediaPipe landmarks on top. It reads as an illustration rather than a photo; the live camera replaces it.
15. **Collapsed pill follows ref 2** (round live thumbnail + green dot + "fastASL" + chevron) rather than ref 3's camera-icon variant, as the brief specifies. The palm-hold progress ring wraps the thumbnail.
16. **Feed aspect varies slightly by state** (16:10 by default, taller in Ready/Recognizing like ref 3, shorter in Agent ready/Settings) to match the references' proportions while keeping the 300/340px widths.
17. **Gesture hints are tiny gray lucide icons + words** ("👍 send · ✊ cancel" without emoji color), so the palette stays monochrome (green dot/check and the red dictation dot are the only colors).
18. **Controller hardening from the test pass** (102 vitest tests in `app/controller.test.ts`): late agent events after Stop are ignored (late confirms are auto-declined), a Stop before the agent starts prevents the run, "thinking" can't get stuck or be overwritten by a stale answer, and failed results stay up 8s (matching their progress line) instead of 4s.

## Phase 2 — Camera

19. **`app/engines.ts` is the single owner of the camera pipeline** (and, from Phase 3, the gesture and recognition engines). App starts it once the saved settings are loaded, but never in screenshot / stage mode or with `?mock=1`, so screenshots always show the mock hand. Camera settings reach it through the store, not through direct calls: `controller.toggleCamera()` sets `cameraOn` and the new `controller.setCameraSource()` sets `cameraSource` (used by the finger pick and the URL field); engines.ts subscribes to both and calls `setEnabled` / `setSource`. That way the controller never imports the engine (no import cycle once the gesture engine calls back into the controller), and the store stays the renderer's one copy of the settings. `subscribeFrames(fn)` fans every tracked frame out to later phases; an empty frame is sent whenever the camera goes away so no consumer holds stale hands.
20. **MediaPipe assets are bundled locally, SIMD build only.** `scripts/fetch-assets.mjs` (run by `postinstall` and `npm run setup`) copies `vision_wasm_internal.{js,wasm}` from `@mediapipe/tasks-vision` and downloads the pinned `float16/1` `hand_landmarker.task` (7.8 MB, MD5 checked against Google Cloud Storage's `x-goog-hash`, written via `.part` + rename). Skipping the non-SIMD build saves ~26 MB; Electron always has SIMD. The ~21 MB of generated files live in `src/renderer/public/mediapipe/` (gitignored) and electron-vite copies them to `out/renderer/mediapipe`. They resolve relative to `location.href`, which works from both the dev server (http) and the built app (file://) under the existing CSP, so the `assetBase` IPC / `fastasl-asset:` scheme stay unused. MediaPipe's telemetry POST to `odml.pa.googleapis.com` is blocked by the CSP; it only logs a console error, and we leave it blocked. Loading from inside `app.asar` (a packaged build) is untested.
21. **ESP32-CAM streams go through a local CORS proxy** (`src/main/camera/mjpegProxy.ts`), started in `boot()` (not in screenshot mode) and closed on `will-quit`. Embedded cameras never send `Access-Control-Allow-Origin`, and without it the `<img>` taints the canvas and MediaPipe can't read it. The proxy binds 127.0.0.1 on a random port and every URL carries a per-launch token (403 without it), because a CORS-open local relay could otherwise be used by any web page to read LAN devices. If the proxy fails to start, only MJPEG sources fail ("Can't reach the ESP32 stream"); the built-in camera still works.
22. **One 5s timeout, passed as the `timeout` request option, covers connecting and stalls.** The option arms the socket idle timer before DNS + TCP connect; `req.setTimeout()` only arms after `'connect'`, which left an unplugged ESP32 or a wrong IP hanging ~75s. The same timer ends a stream that stops sending (a Wi-Fi drop leaves the socket open). The renderer's 8s limit is a backstop.
23. **The renderer asks the proxy with `fetch()` before loading the `<img>`**, because an `<img>` can't read error text: this gives specific messages (camera unreachable / URL is a web page, not a stream / unsupported scheme) without waiting for two timeouts. A stream that breaks off is detected by the image going blank (`naturalWidth` 0, Chrome fires no `error` on a broken multipart `<img>`) and reported as "Lost the ESP32 stream".
24. **The proxy hangs up on the camera when the renderer leaves, and each stream gets its own socket (`agent: false`)**, because ESP32 firmware serves one stream client at a time. Verified in the smoke test: switching source or turning the camera off makes the mock camera log "client left" immediately.
25. **For MJPEG the canvas is the single frame source.** Each animation frame copies the `<img>` into a canvas that MediaPipe and the Feed both read (never tainted, resizes with the stream). Known trade-off: `<img>` has no per-frame event, so a 15 fps ESP32 stream gets ~30 detections/s (each frame processed twice, ~10 ms each on the main thread). The fix, if needed, is to `fetch()` the stream, split the parts and use `createImageBitmap`.
26. **The built-in camera's `deviceId` is `ideal`, not `exact`**: if the chosen camera is unplugged, any camera beats none for this audience. Video frames are scheduled with `requestVideoFrameCallback` (fires 30/s even on a `<video>` that is not in the page), the MJPEG canvas with `requestAnimationFrame`.
27. **Hand tracking: GPU first, CPU fallback, ~30 detections/s.** `HandLandmarker` runs in VIDEO mode with 2 hands; detection confidence 0.6 (fewer false hands), presence and tracking 0.5 (sticky). One warm-up inference on a blank `ImageData` at load time catches GPU failures early enough to fall back to CPU and moves shader compilation off the first camera frame. Timestamps are forced to increase (MediaPipe rejects equal or earlier ones). Detections are throttled to one per 26 ms: ~29 ms lost frames to jitter (22 detections/s on a 30 fps camera), 26 ms measured 28.5/s and still caps 60/120 Hz displays at ~30/s.
28. **Pipeline recovery.** A session counter makes stale async work discard itself; the tracker is shared across sources and rebuilt after an inference error. Failures fall back to the mock hand with `live.error` set and retry with backoff (1s doubling to 10s, reset once frames actually flow), except missing MediaPipe files (33). Only a backoff retry of the same source keeps the last error visible (no flicker); `start()`, a real source change and turning the camera back on clear the error and reset the backoff, so an old source's error never shows while a new one opens.
29. **Motion energy (drives the activity bars) is measured in hand sizes per second**: hand size is the larger of wrist→middle knuckle and index→pinky knuckle, so it doesn't depend on distance to the camera; hands are paired between frames by nearest wrist (handedness labels flicker); x is corrected for aspect; speeds under 0.3 hand sizes/s are jitter, the rest goes through tanh(speed/3) and a 150 ms time constant, so 15 and 30 fps behave the same.
30. **The macOS camera prompt is only requested when the built-in camera will be used** (saved source is built-in and the camera is enabled). An ESP32-only setup never sees a camera prompt. Switching to the built-in camera later relies on `getUserMedia` to raise the prompt (not verified, to avoid permission prompts while testing); if it doesn't, the next launch asks at boot because the saved source is now built-in.
31. **Dev diagnostics.** In dev the full feed shows a tiny gray tabular "30 fps" top-right while the live camera runs (hidden with the mock hand, so screenshots are unchanged), and engines.ts logs a `[camera] live 640x480 · 30 fps · 1 hand(s)` line whenever that status line changes (checked every 2s). `FASTASL_LOG=1` forwards the renderer console to the main process's stdout and `FASTASL_DATA_DIR=<dir>` overrides the data directory, so a smoke test can launch the built app with its own `settings.json` and read the camera status from the terminal.
32. **`npm run mock:mjpeg` stands in for an ESP32-CAM** at `http://127.0.0.1:8081/stream` (`multipart/x-mixed-replace;boundary=frame`, plus `/capture`), fed by ffmpeg from the Mac camera or, with `--test`, a 15 fps test pattern that needs no camera permission. It runs ffmpeg continuously, binds 127.0.0.1 and drops frames for slow clients the way a real camera does. Requires `brew install ffmpeg`; no new npm dependencies.
33. **The tracker loads before the camera opens, and missing MediaPipe files are a permanent, readable error.** Opening both in parallel saved a few hundred ms on the first launch, but a tracker that can't load then opened and closed the camera on every retry (the green light blinking forever, an ESP32 reconnect each time). Now the tracker comes first (it is cached, so later restarts don't wait for it). Before loading, `createHandTracker` fetches the wasm loader, the wasm binary and the model (local files, the body is cancelled) and throws `MissingAssetsError` if any is missing: on file:// a missing file rejects, and the dev server answers with its `index.html` (200, `text/html`), so HTML counts as missing. The card shows "Hand tracking files are missing — run npm run setup" (like "Add <KEY> to .env") and the pipeline stops retrying, since the files won't appear by themselves; a relaunch, the camera toggle or a new source tries again. Covers a failed `postinstall` (offline, firewall), `npm ci --ignore-scripts` and a deleted `public/mediapipe`. Any other load failure that rejects with a DOM `Event` (a `<script>` that didn't load) becomes "Hand tracking failed to load (the MediaPipe runtime script failed to load)" instead of "[object Event]", and still retries with backoff without touching the camera.
34. **`store.getSettings()` validates the camera source.** Main (`boot()` reads it for the camera prompt) and the renderer (through IPC) both read settings there, so one check covers both. Anything other than `{kind:'builtin', deviceId?: string}` or `{kind:'mjpeg', url: string}` falls back to the built-in camera. Before, a hand-edited `"cameraSource": null` threw inside `boot()` after the dock icon was hidden, leaving the app running with no window and no tray icon.

## Phase 3 — Gesture engine

35. **`GestureEngine` (`src/renderer/src/engine/gestures/`) is pure and deterministic; `app/gestureInput.ts` connects it to the app.** `connectGestures(controller, subscribeFrames)` feeds it every frame from the camera pipeline (frames with no hands included), sends each fired gesture to `controller.gesture()` (which gates by view a second time), and on every view change calls `setActive(activeGestures(view))` (via `useApp.subscribe`), so the engine only evaluates, fires and shows progress for gestures the current view accepts. The sensitivity setting maps to `SENSITIVITY[s]` (hold times × `holdScale`, swipe distance/speed × `swipeScale`) and applies immediately. `startEngines(controller)` now takes the controller from App instead of importing the singleton, so `engines.test.ts` drives the real wiring (synthetic frames → engine → real `Controller` on mock services → store) without `context.ts`'s `location`-based service pick. The engine costs a few µs per hand per frame, so it stays on the renderer's main thread. No new dependencies.
36. **Hold progress goes to the store only when it changes.** `holdProgress` fills the collapsed pill's ring and `pick` the option badge's ring; both are compared with the store before each write, so idle frames cause no React renders (a hold renders at camera rate, ~30/s, for its 0.5–1 s). While the live camera runs the engine owns both fields: a dev scene's mock ring (the tray's "Collapsed + palm hold" scene, the quick menu's pick) disappears on the next frame. Screenshots and `?mock=1` never start the engines, so they keep the scene values. Dev-simulated gestures (Ctrl+Opt hotkeys, dev panel) still call `controller.gesture()` directly and bypass the engine. The engine's custom-shape progress (`progress().shape`) has no store field yet.
37. **A new camera session starts the engine from scratch.** Every camera session (new source, restart after a failure, camera turned back on) opens a new `<video>`/`<canvas>`, so a change of `live.source`, or of the frame's aspect ratio (an ESP32 can change resolution mid-stream), triggers `setAspect(width / height)` and `reset()`: no tracks, holds, cooldowns or armed hands-down carry over (otherwise a phrase could end the instant the camera came back after hands had gone down). Frames that arrive while `live.mock` is set are not real hands and are skipped; the pipeline sends one such empty frame when the camera goes away, which clears any half-filled ring. A store subscription on `cameraSource` was rejected because a failure retry changes no setting and the new source's size is only known once frames flow. Cost: spent holds are forgotten too, so fingers still held while Settings › Camera source switches the camera pick the same row again once the new feed appears, which re-selects the source that is already active (no restart).
38. **Swipe direction follows the mirrored preview.** MediaPipe landmarks are raw camera coordinates, but the feed is drawn mirrored, so a hand moving toward the left of the preview (the user's own left) moves +x in the raw frame. Raw +x is reported as `swipeLeft` (previous mode in Ready/Dictation, delete last word while building and in Sentence, previous teach page), raw −x as `swipeRight` (next mode, proceed). The direction does not depend on the Left/Right handedness label. Checked end to end: an MJPEG stream of a hand photo sliding +x fired `swipeLeft in ready` and the mode went command → spell; sliding −x fired `swipeRight` (spell → command).
39. **Geometry is aspect-corrected.** Landmark x and z are multiplied by width/height before any shape or speed math; without it a 16:9 frame squashes sideways shapes by 1.78×. Swipe distances are still measured in frame widths and heights.
40. **Shape rules return nothing when unsure.** A finger counts as extended when the average of two signals (bend between proximal and distal phalanges; fingertip-to-wrist over PIP-to-wrist distance) is ≥ 0.7, folded at ≤ 0.3, "partial" in between, so relaxed and C hands never trigger controls. The thumb uses chord ÷ path straightness (its short segments make joint angles jittery), capped by its reach from the index knuckle. Open palm uses |palm facing| (handedness labels are unreliable). Counts 2 and 4 need a folded thumb, 1–4 an upright hand, 5 an open palm. ASL A falls in a deliberate gap between fist and thumbs-up (fewer false cancels while fingerspelling); a thumbs-down reads as a fist ("no" either way). Priority when a hand matches several: thumbs up > fist > palm hold > fingers > custom shape > built-in peace, among active gestures only.
41. **Holds: 1.0 s palm, 0.8 s fingers and shapes, 0.9 s fist, 0.5 s thumbs up** (the strictest shape test, so it can be shorter), times × `holdScale`. Timing starts at the first frame of the stable run; 1–2 frames of a different reading or a dropped hand don't reset it, the third does. Every visible hand must be still (wrist < 0.8 palm lengths/s over 200 ms), so a passive base hand under a moving dominant hand never completes a fist, and a hold never fires on a moving frame. Signs change handshape every ~150–400 ms, well under any hold.
42. **Release and cooldowns.** After any event the engine is silent for 700 ms, and the same gesture and parameter (`fingers:2`, `shape:<id>`) can't refire for 1.5 s. A fired hold must also be released before it can start again, even across view changes: no hand may show it for 300 ms (`RELEASE_MS`). The release is timed rather than counted in frames. At first, 3 frames without the gesture counted as letting go, so a 100 ms tracking dropout or a short misread re-armed a thumbs-up that was still up. It then refired once the 1.5 s cooldown ended, and by then the view had moved on: a thumbs-up kept up in Sentence proceeded and then started the agent, and one kept up in Agent ready then approved the confirm step. 300 ms is longer than a dropout and shorter than any deliberate release, which is followed by a 0.5–1 s hold anyway. Holding a fist after it cancels the quick menu therefore does not also collapse Ready. A hold blocked by a cooldown fires as soon as the cooldown clears.
43. **Swipes need a long, fast, straight stroke by a flat hand while other hands rest:** ≥ 0.22 frame widths (≥ 0.20 heights up) within 300 ms, peak speed ≥ 1.2 widths/s (over ≥ 60 ms, see 48), main axis > 2.2× the cross axis, the hand flat in at least half the window. Guards against signing and accidents: only motion after the hand was first seen at rest (≥ 100 ms) counts, so raising a hand into view is not a swipe; each stroke is decided once (fired or discarded) and the rest of its motion is ignored until the hands rest; the opposite swipe is ignored until 1.2 s after the swipe's motion ends (return stroke); a swipe that interrupts a hold at least 60% done is discarded; and the shapes the swiping hand showed are spent, so holding the open hand still after a swipe in Settings doesn't pick option 5. Hands are matched across frames by wrist position, globally and closest first, so a second hand appearing next to a held one can't take over its track (which would read as a jump and a swipe).
44. **Both hands down arms only after 3 frames with hands and fires once** (1.2 s × `holdScale` after the last hand), then waits for hands to return. Entering a view that accepts it with the hands already down does not fire it.
45. **The built-in peace sign is reported as shape `builtin-peace`** and reaches `controller.runShortcut` in Ready and Collapsed (mock services until Phase 5, so it only shows the toast). `GestureEngine.setShapeMatcher` for custom gestures is not wired yet: the "New gesture" capture flow comes in a later phase. The matcher keeps running while a custom shape is spent, so a shape held through its toast won't fire twice.
46. **Dev diagnostics.** In dev every fired gesture logs `[gesture] <gesture[:param]> in <view>` (the view it fired in, before the controller acts); with `FASTASL_LOG=1` it reaches stdout next to the `[camera]` line.
47. **Every new view needs a fresh gesture.** When the view kind changes, `gestureInput` calls `engine.spendShown()`, which marks every gesture shown at that moment, or within the last 300 ms (a dropout just at the change), as spent. A thumbs-up raised while the agent works therefore can't approve the confirm step that appears under it, and a hold in progress restarts from zero in the new view. It runs only on a change of kind, not on every view update, because the Working card is replaced on each agent step: spending there would keep a held stop-fist from ever completing. Settings pages share one kind, so moving between them doesn't spend anything. Fingers picks are spent when they fire, so this needs no extra rule.
48. **Swipe peak speed is measured over at least 60 ms (`SWIPE.speedSpanMs`), not frame to frame.** The pipeline tracks an MJPEG canvas on every animation frame (~30/s) whatever the stream's own rate, so a 15 fps ESP32 or `npm run mock:mjpeg` stream reaches the engine with each image twice, 33 ms apart. The FPS readout then shows about 30, the detection rate. Frame to frame, the speed read 0 and then twice the real speed, so a steady 1 frame width/s reposition passed the 1.2 widths/s gate and swiped (proceed or delete a word in Sentence). It was rejected on a 30 fps camera. Measured from the latest sample at least 60 ms earlier, a repeated image counts as one 66 ms step, and the same span also absorbs frames that arrive bunched or late. On a 30 fps camera that span is two frames, which lowers a real swipe's peak by about 3%. Skipping repeated images in the pipeline (comparing a thumbnail of each canvas) was rejected for now: a static test stream would then stop producing frames, and it would change Phase 2 code that has no DOM tests. Only the swipe speed depends on the sample spacing; holds, release and hands-down are timed, and the flicker tolerance of 2 frames shrinks to ~66 ms on such a stream, the same as on a 30 fps camera.

## Phase 4 — Sign recognition and Teach a sign

49. **The recognition engine (`src/renderer/src/engine/recognition/`) is pure and deterministic, and `app/recognitionInput.ts` connects it to the app.** The engine was built and unit-tested on its own (features, segmenter, DTW, kNN, recognizer, `RecognitionSession`, `TeachSession`, synthetic signer, calibration) and copied in with two edits: `ambiguous` events now say whether the guess is a word or a letter, and pack validation moved to `src/shared/templatePack.ts` (62). `startEngines` subscribes the gesture engine first and recognition second, so a gesture that fires on a frame has already suspended recognition when that frame reaches it. Fired gestures reach the controller through `recognition.gesture()`, which settles conflicts with the sign in progress (54, 55). Recognition follows the store: `templates` (loaded by `controller.loadTemplates()` at startup and after a tray import, saved after teaching), `sensitivity` (`SENSITIVITY[s]`: hold times × `holdScale`, accept thresholds × `acceptScale`) and `mode`. Spell mode, and the Spell a new word page, are letters only; Command and Dictation take words and letters. DTW against a few hundred templates when a movement ends costs a few ms, so recognition runs on the renderer's main thread. No new dependencies.
50. **Features are hand-relative and aspect-corrected.** Each hand is normalized by its own size and position, with x and z multiplied by width/height and z counted at half weight. Hands keep their Left/Right slot by continuity: when both hands get the same label, each keeps the slot of the nearest hand in the last frame (settling it by confidence made the hands trade places every frame, which looked like constant motion). Letter vectors mirror the left hand, so letters work with either hand. A hand's position is the palm centre (the mean of the wrist and the four knuckles), which averages out landmark jitter and doesn't move when only the fingers move. Velocity is smoothed with a 65 ms time constant and capped at 20 hand lengths/s, and a jump of more than 1.5 hand lengths at above that speed (a tracking glitch or a slot swap) counts as no motion. A non-finite or zero aspect (the feed has no size yet) is ignored, so 0/0 can be passed every frame.
51. **Segmentation.** A sign starts when a hand in the signing zone moves its palm faster than 1.8 hand lengths/s. Finger movement alone doesn't start one. It ends after 400 ms below 1.1 hand lengths/s, or 200 ms without hands. It keeps 100 ms before the start and 100 ms after the last motion, and anything shorter than 350 ms or longer than 4 s is rejected. Every `signStart` gets exactly one `token`, `ambiguous` or `rejected`, unless a control gesture or a switch to Spell mode drops it. A letter is one hand holding a shape for 0.5 s × `holdScale` with a drift of at most 0.3 between the mean shapes of the two halves of that window. Drift is used rather than jitter, because jitter is large on small, far hands. A letter fires once, and the next one needs a new shape (measured on a 100 ms smoothed shape), a slide or dip of 0.5 hand lengths, or the hand leaving, so double letters work. A letter never comes on the frame a movement ends, and only a recognized word blocks the shape held after it. Raises, rejected movements and slides don't swallow the next letter.
52. **Classifier thresholds come from a synthetic signer, not real cameras.** Words use DTW nearest neighbour per label on 32-frame resampled sequences (Sakoe-Chiba band 4) and are accepted at a mean frame distance ≤ 1.5 × `acceptScale`. Letters use distance-weighted kNN (k = 3) and are accepted at ≤ 0.7 × `acceptScale`. When the runner-up is another label within best / second > 0.85, the result is ambiguous. `calibration.test.ts` places these values in the gap between known and unknown signs for 10 words and 12 letters with realistic variation (tempo ±20%, amplitude ±15%, timing warp, hand size, ±8° orientation, ~1.6 px jitter, dropped frames). It also covers small, far hands with ~2.6 px jitter: ≥ 95% recognized, and unknown movements rejected. Real MediaPipe output is noisier than the model. If real signs are rejected, raise Sensitivity before changing the thresholds.
53. **Tokens are lower case; labels stay glosses.** Recorded labels are upper case (MEETING), as the teach list shows them. Word tokens are lower-cased on the way to the controller, so sentences read "Meeting tomorrow" and Dictation types `meeting `, not `MEETING `. Letters stay upper case. An ambiguous word opens Did you mean (purpose `sign`, lower-case options) in Ready, Listening, Building and Sentence, and the pick continues the phrase. Dictation takes the best guess and types it, as every view does for an ambiguous letter: a prompt per word or letter would stall typing and fingerspelling, and Spell mode's Claude suggestions fix the word at the end.
54. **Letters vs control gestures: outside Spell mode the gesture wins, in Spell mode the letter does, and either way the shape is spent.** Outside Spell mode a recognized letter is held back until a control gesture with the same shape would have fired: (1000 − 500) ms × `holdScale` + 250 ms after the hold registers, so about 1.25 s of holding at Medium. It is released early as soon as the hand moves on (new shape, slide, hands down, a movement). Every gesture that acts calls `rec.suspend(600)`. That drops the held-back letter and any sign in progress, and blocks the shape still held, so a fist is never also an S and a thumbs-up never an A. Spell mode letters, and those on Spell a new word, arrive with no wait (after 0.5 s × `holdScale` of holding, before a fist's 0.9 s). So there `recognition.update()` reports each letter too, and `startEngines` calls `gestures.spendShown()`: the shape still held can't also fire until it is released. Without this, an S held about 0.4 s too long fired the fist, which left Spell a new word (losing the word) and, from the third letter on (once the view no longer changes kind, 47), cancelled the phrase in Spell mode. The price: on those two screens a fist or thumbs-up whose shape is a taught letter can type that letter instead of acting. Swipes always act there. In Spell mode swipe left deletes the whole spelled word (a run of letters is one word), which cancels it, and swipe right or both hands down end it. On Spell a new word swipe left deletes one letter and, with none left, goes back (60). The other direction is handled too. When a word is recognized, `gestures.spendShown()` marks the handshape still held as spent. The hand usually rests in a word's last shape: TOMORROW ends in a thumbs-up and YES in a fist. On the synthetic signer, the thumbs-up after TOMORROW ended the phrase in 2 of 3 runs in Building before this change. Kind changes already spent it for the first word of a phrase (47).
55. **A recognized word beats a swipe made by the same movement.** The synthetic MUSIC (a flat hand sweeping sideways, a starter word) fires `swipeRight` in every run. From Ready it switched the mode to Dictation, and in Building it ended the phrase, so MUSIC could never be signed. Holds can't be confused this way (they need stillness), but a swipe is a movement. So while recognition is judging a movement (between `signStart` and its outcome) and any word is taught, a swipe waits for the verdict. A recognized or ambiguous word drops it; a rejected movement lets it act. A swipe still waiting 1.5 s after it fired (the hands kept moving) is dropped. Cost: in views that take signs, a mode swipe or the swipes in Building and Sentence act when the hand stops (about 0.4 s later) instead of at the end of the stroke. With no word taught, swipes act at once. In probes on the synthetic hands, 1 of 12 deliberate swipes read as HELLO (a flat hand moving the same way) and became the word.
56. **Listening is still Ready for control gestures.** Raising a hand into view is a movement, so it shows Listening (`recognizing` with no token) and then, unless it was a sign, `rejected` brings Ready back (`controller.signRejected()`; it keeps a quick-menu pick's hint, because `idleView()` now includes it). If Listening had the phrase gestures and counted as a new screen (47), a fist raised to collapse the card would have been spent on the way up, and a thumbs-up would have ended an empty phrase instead of opening the quick menu. So `activeGestures` gives Listening Ready's set, the controller handles it like Ready, and `gestureScreen()` treats Ready and Listening as one screen when deciding what to spend. A gesture that acts during Listening leaves no sign to wait for, so `applyGesture` also calls `signRejected()`.
57. **Which views take signs.** `takesSigns(view)` is true for Ready, Listening/Recognizing, Building, Sentence, Dictation and Settings › Spell a new word. Collapsed, menus, Did you mean, agent cards, toasts and the other settings pages get no recognition, so a menu pick by fingers is never also a V or W. Teach › record feeds its own recorder (58). Coming back to a view that takes signs, or a new camera session, resets the session (`suspend(0)`): no stale motion, and the shape held as the view appears must change or leave before it reads as a letter. That matches 47 for gestures: the two fingers that picked "Send message" are not a V in the Ready that follows. Frames while the feed shows the mock hand are skipped. A movement dropped by these resets still gets an outcome, `signRejected()`, so Listening doesn't stay up when the camera goes away or changes mid-sign. The pipeline switches to the mock hand before it sends its "hands gone" frame, so that frame can't end the movement.
58. **Teach › record uses its own `TeachSession` and its own segmenter, which starts blocked.** Opening a record page (a label not being recorded yet) starts a session for 5 repetitions of a word or a letter (139; 10 for words before). Without the block, the hand that picked the sign by fingers (still up) was recorded as the first repetition: "1 of 5" before anything was signed. `listening` marks the page (`listening: true`: a green pulsing "Listening..."), and each `progress` shows `done` exactly as given, plus the reason a repetition wasn't kept. Raising and lowering the hands between repetitions are silent. The kept repetitions are the largest group that agree with one another (within the recognizer's accept threshold), ranked by clean members (started with the hands already in view and ended holding still), then size, then the newest attempt. A fumbled first try is outvoted and `done` can stay flat or even drop. When complete, `controller.teachLearned` reads signs.json (not the store, since a pack may have been imported meanwhile), appends the new templates with `mergeTemplates` (new ids only), saves, puts them in the store (recognition reloads), and shows the toast "Learned MEETING · 5 recordings saved". The toast returns to the teach list on that sign's page. A failed save toasts "Couldn't save MEETING" with the error. Teaching a sign again adds templates instead of replacing them (nearest neighbour gains coverage, and the list count grows). Templates are 32 frames rounded to 3 decimals. If the camera goes away or changes mid-repetition, the recorder's segmenter starts over and the page gets `teachProgress` with the current count, which ends "Listening...".
59. **On a letter's record page the way back is swipe left, not a fist.** S, T, M, N (and maybe E) are held still and read as a fist, so with fist = back, teaching S left the page after one repetition. Letter record pages accept only `swipeLeft` (back to the list), and word pages only `fist`, so the finger counts and shapes that letters look like (V, W, B) never pick or fire anything while recording. The hint says which. Known risk: YES is a fist nodding at the wrist, and the gesture engine's stillness test watches the wrist, so a pause of 0.9 s or more in the S shape after YES can still leave a word's record page. Lower the hand between repetitions.
60. **Spell a new word: fingerspelled letters, or the keyboard.** While the page is open, recognition is letters only. Each letter is appended, swipe left deletes one (and with none left goes back to the list, because a taught S held there is a letter rather than a fist, 54), and thumbs up records the word (`teachRecord`, kind word, 5 repetitions). A keyboard button opens a text field that makes the window focusable only while it is open, like the stream URL (the overlay must never steal focus, so it doesn't open on its own, even with no letters taught; the subtitle then says "No letters taught yet: type the word", from the page's `canSpell`, 61). Every keystroke goes through `controller.setTeachWord`: upper case, A–Z, 0–9, space, apostrophe and hyphen, at most 32 characters. So typing and fingerspelling edit the same word, and Return equals thumbs up.
61. **The teach pages carry what they show about the recorded signs.** `teachPick` has `recorded` (templates per label), and a recorded row shows "10 recorded" on the right (`OptionList` `detail`). `teachSpell` has `canSpell` (some letter is taught), which picks its subtitle. Both are worked out when the page opens and again by `loadTemplates()` while it is open, so a tray import updates an open list at once. They live in the page, not in a store selector, so the screenshot scenes decide them (YES 10 and HELLO 20; KRIS fingerspelled) and the screenshots don't depend on the developer's signs.json. Back from a record page (fist, swipe or X) returns to the list on that sign's page. Spell a new word returns to the first page. A toast can now return to a settings page (`returnTo: SettingsPage`), which the teach flow uses.
62. **Template packs are validated in one shared module.** `src/shared/templatePack.ts` (format `fastasl-template-pack`, version 1, ids ≤ 200 chars, labels 1–64, kinds word/letter, 2–512 frames of 134 numbers per word and 1–512 of 63 per letter, finite numbers, unique ids) is used by the main process (`store.importTemplatePack`, the `importPack` IPC, the tray) and by the renderer's tests. Main can't import renderer code, so the vector sizes are repeated as `TEMPLATE_DIMS`, and `pack.test.ts` checks them against the feature layout. In the dev tray, "Import template pack…" opens a file dialog and merges by id (existing templates are kept, duplicates skipped). It tells the renderer to reload (`templatesChanged` dev command) and reports "Imported N new template(s)". An invalid pack shows an error box with the validator's message and leaves signs.json untouched. "Export template pack…" saves every template (default `~/Desktop/fastasl-pack.json`). The app has no Dock icon, so both call `app.focus({ steal: true })` first, or the dialogs open behind other apps. `npm run templates -- export|import|stats` does the same from the command line. It repeats the validation rules (`pack.test.ts` checks that both reject the same packs) and now honours `FASTASL_DATA_DIR` like the app.
63. **Dev diagnostics.** In dev, every recognition event logs `[sign] <start | hello (word) | L (letter) | a or b? (word) | rejected> in <view>`, the recorder logs `[teach] listening` and `[teach] 3/5 (reason)`, a swipe held or dropped by 55 logs `[gesture] swipeRight waits for the sign` / `... dropped: the movement was a sign`, and each template load logs `[signs] N template(s) for M sign(s)`. `FASTASL_LOG=1` prints them to stdout next to `[gesture]` and `[camera]`.

## Phase 5 — Claude (intent, Did you mean, context actions)

64. **Claude runs in the main process (`src/main/claude`), and the client is built on first use.** `createClaudeService({ tools })` provides `MainServices.interpret` and `spellSuggest`. The Anthropic client is created lazily (`maxRetries: 1`) and rebuilt only when the key changes, so it doesn't matter that `loadEnv()` runs first. A missing `ANTHROPIC_API_KEY` returns `{ ok: false, error: 'Add ANTHROPIC_API_KEY to .env', missingKey }` without touching the network. There are no new dependencies. The SDK's `zodOutputFormat` helper takes zod 4 schemas, which zod 3.25 already ships as its `zod/v4` entry, so only `src/main/claude` imports `zod/v4`. The rest of the app, and the Droid SDK (3), stay on zod 3.
65. **Model and request shape.** The model is `claude-sonnet-5-5`. Replies are strict JSON through `output_config.format`, built from the same zod schema that validates them. The request uses `effort: 'low'` and `thinking: { type: 'between_tools' }`, the lowest setting Sonnet 5.5 accepts (`disabled` returns a 400), and the server-side refusal fallback is on. The system prompt (instructions plus the tool list) is cached. Each request is one JSON user turn, and the prompt says everything in it, window titles included, is data and never instructions. The API ignores min/max limits in the schema, so `sanitizeIntent` clamps them instead (67).
66. **Each call has one 15 s deadline and gets one correction retry.** `askJson` gives every attempt the same `AbortController`, so the SDK's own retry (network errors, 429, 5xx), its backoff and `retry-after` waits, and our correction retry all share the 15 s. The correction retry covers invalid JSON, a schema mismatch or a `max_tokens` cut-off, and the bad reply is echoed back as an assistant turn. After the deadline the answer is "Claude took too long to answer". SDK errors become short messages for the card: "Can't reach Claude. Check your connection", "Claude is busy right now. Try again in a moment", and "Claude declined to answer this one" for a refusal. A 401 becomes "Claude rejected ANTHROPIC_API_KEY. Check .env" with no `missingKey`. The controller turns any `missingKey` into "Add … to .env", which would be wrong for a key that is present.
67. **What `interpret` guarantees the card.**
    - Outside Command mode `intent` is always null, and a blank intent is null.
    - Alternatives never repeat the intent. Both lists are de-duplicated ignoring case and capped at 3.
    - Confidence is clamped to 0..1. An empty sentence falls back to the draft, then to the tokens.
    - `needs_confirmation` is false without an intent. Otherwise it is the model's flag, raised (never lowered) when any clause of the intent starts with a side-effect verb (send, email, text, create, schedule, delete, buy…). "Open Mail and send…" counts; "Play Post Malone" doesn't.
    - The controller doesn't act on `needs_confirmation` yet. Agent ready is already a confirmation step, and from Phase 6 the Confirm card guards every write tool.
68. **The prompt lists the agent's planned tools from `src/main/claude/toolCatalog.ts`.** The agent arrives in Phase 6, but Claude should already phrase intents as things the agent will be able to do. A static catalog of the 14 planned tools (name and one line each) stands in until Phase 6 replaces it with the real registry (`src/main/tools`, same names). `tools` is a function read on every call, so the registry can change without rebuilding the service. Each request also carries the frontmost app (name, bundle id, window title), the quick-menu prefix and the saved gestures (name and task). In dev, the terminal prints one `[claude] interpret <request> -> <answer>` (or `spellSuggest`) line per call, so the context sent and the card's routing can be checked against what Claude said.
69. **Frontmost app comes from `src/main/mac/frontmost.ts`.** `getFrontmostApp` caches for 300 ms, and concurrent callers share one lookup.
    - The app name and bundle id come from NSWorkspace through JXA, which needs no permission.
    - The window title is read from System Events at the same time, with a 1.5 s timeout, and is left out when that fails. It needs Accessibility, and the first call may show macOS's "control System Events" Automation prompt; the timeout keeps the prompt from holding up the interpretation.
    - The overlay never takes focus, so when a phrase ends the frontmost app is the one the user is signing about.
    - `osascript.ts` is copied from the Mac-tools module as a whole, because frontmost uses it and the Phase 6–7 tools build on it.
70. **Real services by default, mocks on request.** `app/context.ts` uses the IPC services except in three cases: the screenshot stage, `?mock=1` (which also keeps the camera off, 19) and `FASTASL_MOCK=1`.
    - The env var reaches the renderer as `--fastasl-mock` and `window.fastasl.mockServices`. It keeps the camera live, so you can sign against mocked Claude, agent and typing without keys or side effects.
    - Until Phases 6 and 7, `agentRun` answers "The agent is not available yet": the Done card reads "Couldn't start the agent" and collapses after 8 s. `typeText` answers "Typing is not available yet": Insert text toasts "Could not insert text".
    - Dictation now shows a typing failure as a notice, so dictating into nothing is no longer silent. Every `typeText` call is wrapped like the other IPC calls, so a rejected call can't leave the card stuck.
71. **How a Claude answer is routed (Sentence, then thumbs up or swipe right).** The checks run in this order:
    - **Did you mean, numbered.** Used when confidence is below 0.6 (with an intent or alternatives), or when there is an intent with alternatives and confidence below 0.75. That second case covers "close alternatives": the API returns one confidence, not one per alternative, so a close call means the model wasn't sure of its intent and listed a runner-up. The intent comes first, then the alternatives, at most 3. A lone intent is a list of one, so the action that would run is always on screen. Fingers pick (thumbs up picks 1), and a pick opens Agent ready, never the agent itself. Swipe left goes back to the Sentence to edit it, and a fist cancels. The list shows the hint "hold up 1–N fingers · swipe ← edit".
    - **With no intent**, the alternatives are Claude's candidate intents, and "Insert text" comes last. A sentence Claude can't act on may be text to type ("thank you for the update" with TextEdit in front), and without that row the only ways out were a candidate intent or a fist. It types Claude's sentence, as Context actions do.
    - **The quote variant ("Did you mean?", Yes, send / Edit) is not used for intents.** It shows the sentence, not the intent, so "Yes" would run an action the user never saw, and a guessed intent is exactly when that matters. From Phase 6, read-risk tools (play music, open an app, type text) run with no Confirm card. The variant stays as a design state (screenshot 17), and its Yes now opens Agent ready too.
    - **Context actions.** Used when there is no intent and Claude isn't guessing. "Insert text" (first) and "More options" (last) are always there. Up to 2 of Claude's actions for the frontmost app go between them, for at most 4 rows (4 fingers, 12). Claude's own insert, type and "more" entries are dropped as duplicates. That way the brief's two paths, typing into the focused app and the quick menu, don't depend on what the model listed. This replaces the old dead end, "No action found" on the Sentence card.
    - **Agent ready** in every other case. The email variant is used when the intent holds an address.
    - The prompt now says alternatives are intents in Command mode (also when the signing was too ambiguous for one) and should be close contenders only. That keeps the lists meaningful for this routing.
72. **Context actions and the quick menu.** "Insert text" types the sentence into the focused app (typing is wired in Phase 7). "More options" opens the quick menu. Any other action prepares Agent ready with `<action>: "<sentence>"`, and the agent also gets the frontmost app. Picked from Ready, a quick-menu option sets the prefix and waits for the details ("Create event: sign the details"). Picked via Context actions › More options, a phrase already exists, so the pick interprets that sentence at once with the prefix (for example "Create event" + "Team lunch Friday noon") instead of throwing it away. The view records where the menu came from (`quickMenu.fromSentence`, set only by More options). Inferring it from leftover tokens went wrong whenever a phrase outlived its card (75). When Claude can't answer (no key, offline, timeout), the fallback intent keeps the pick: Agent ready shows `Search web: Thank you update`, not the bare sentence.
73. **Without a key, every Claude feature degrades on its own.** Sentence › proceed shows the "Add ANTHROPIC_API_KEY to .env" notice and still offers Agent ready with the raw sentence (after a quick-menu pick, `<pick>: <sentence>`), so the agent can try it from Phase 6. Spell mode offers the raw letters as the only spelling, with the same notice. A wrong key shows "Claude rejected ANTHROPIC_API_KEY. Check .env". Smoke-tested in the built app without a key: interpret and spellSuggest return the missing-key result, blank letters return `[]` without a call, and the card goes Sentence → Agent ready (notice) → "Couldn't start the agent · The agent is not available yet".
74. **Spelling suggestions stay within what was spelled.** `spellSuggest` returns up to 3 completions or corrections. The model has no contact data, so the prompt forbids adding surnames, domains or extra words. An email address is allowed only when the letters contain "@", and code drops any suggestion with an "@" when the letters have none. The controller still asks once the phrase ends, puts the raw letters first, and drops a reply that arrives after the view changed (cancelled, or the user kept spelling).
75. **An agent run uses up the phrase.** `runAgent` clears the tokens, the pending interpretation and the quick-menu prefix as it starts. However the run ends (done, a failed start, an error or Stop), the next phrase starts empty. Before, only the done event and Stop cleared them. Until Phase 6 every run fails to start, and the Done card's swipe up (Settings) or 3 fingers (Save as gesture) cancel its auto-collapse. Backing out of Settings then reached a Ready that still held the old tokens: the next sign was added to "Meeting tomorrow", and the quick menu treated the leftovers as More options' sentence. Opening Settings also clears the phrase, because its back button always leads to a fresh Ready, never to the phrase, and the mouse's settings button works from any card.

## Phase 6 — Agent (Factory Droid with in-process Mac tools)

76. **The agent (`src/main/agent`) and the Mac tools (`src/main/tools`, `src/main/mac`) were built and unit-tested on their own, then copied in.** `boot()` calls `createAgentServices()` and plugs `agentRun`, `agentStop`, `agentRespond` and `runShortcut` into `MainServices`; `ipc.ts` already broadcast agent events to every window and needed no change (`ipc.test.ts` now checks the wiring end to end on a scripted Droid session). The agent is not created for screenshots or with `FASTASL_MOCK=1`, whose renderer never calls it, so neither starts a droid process. The tools' `mac/typeText.ts` serves the agent's `type_text` tool only; the renderer's Dictation and Insert text keep answering "Typing is not available yet" until Phase 7 wires `MainServices.typeText`. `lastRunCalls()` (the calls of the last completed run) is kept for the gesture capture flow, which arrives later. No new dependencies: `@factory/droid-sdk` 0.10 was installed at setup (3).
77. **The droid CLI is required, and a missing piece fails only the agent.** The SDK runs the agent by spawning the `droid` CLI (`droid exec … stream-jsonrpc`), so it must be installed (`brew install --cask droid`). `resolveDroidPath()` tries `FACTORY_DROID_PATH` (optional, documented in `.env.example`), then `command -v droid` in the user's login shell (an app opened from Finder gets a minimal PATH), then `~/.local/bin`, `~/.factory/bin`, `/opt/homebrew/bin` and `/usr/local/bin`; nothing is cached, so installing droid needs no restart. At launch the session is opened in the background (`init()`), and a failure is logged (`[agent] session not started: …`) but not cached. Sending a command then shows Done "Couldn't start the agent" with "Add FACTORY_API_KEY to .env" (`missingKey`), "Install the droid CLI: brew install --cask droid", or "FACTORY_DROID_PATH (/nope/droid) is not an executable. …". Compiled shortcuts, the peace sign included, replay without the model and work without either. Smoke-tested in the built app for all three cases. The droid process runs in an empty folder (`<data dir>/agent`), so no project files are within its reach.
78. **One persistent Droid session, one run at a time.** The session (and the warm droid process) lives across commands; each command is one turn carrying the full time context (local date and time, ISO, IANA zone, UTC offset), the frontmost app, the signed sentence and the task. A new run stops the active one first and waits up to 3 s for it; only a stuck agent turn costs the session, which is then replaced (a slow compiled replay never touched it). A stream that throws closes the session, which is re-created on the next command; the turn is retried once only if nothing ran yet, because a retry after a tool could repeat a write. On quit, `before-quit` holds the exit until the session is closed (at most 3 s), which ends the droid process. `dispose()` also marks the service disposed and counts as a stop: a command still queued (say, waiting on a droid that is still starting) ends as "Stopped", and no session opens after it, so a command sent during the quit can't spawn a second droid that nothing closes.
79. **Droid permission mapping.** The session runs at `AutonomyLevel.Off`, so every tool use reaches our permission handler:
    - fastasl read tools (lookups, `contacts_find`, open app, play and pause, web search, type text, screenshot): ProceedOnce, with no card.
    - fastasl write tools (`calendar_create_event`, `mail_send`, `message_send`): the Confirm card. Thumbs up (or Confirm) answers ProceedOnce; a fist (or Cancel/X) answers Cancel and marks the run declined.
    - anything else (Droid's built-ins, other MCP servers): Cancel, and the tool is logged.
    A confirmed write also gets a one-use approval that the in-process tool handler consumes, so a write can't run unconfirmed even if droid skips the permission step; approvals are kept only when the whole request was allowed. A write with invalid args gets no card: the SDK rejects it before it runs, and the model retries with valid ones, which get the card.
80. **Droid's built-in tools are restricted four ways.** The SDK has no allowlist, so: every listed tool that isn't ours goes into `disabledToolIds` after start; Autonomy Off routes everything through the handler above, which cancels non-fastasl tools; the session runs in an empty folder with builtin skills off and AskUser cancelled; and the system prompt says to use only the fastasl tools. MCP tool ids are undocumented, so foreign ids are disabled only when every fastasl tool was recognised in `listTools()`. Otherwise only `source: 'native'` tools are disabled, and a warning lists the other ids, because a format the matcher misses would otherwise silently disable our own tools. The disabled ids are always logged (`[agent] disabled droid tools: …`). Names match exactly or as `…fastasl<separator><name>`. **Not verified live:** the droid CLI isn't installed on the build machine and there is no `FACTORY_API_KEY`, so the real id format, the disabled list, the warm-PID behaviour and quitting killing droid are checks for a human (TESTING Phase 6, steps 5, 6, 15, 22 and 26).
81. **Evidence rule: the Done card comes from tool results, never from the model.** Tools run in the in-process MCP handler, which records `{tool, args, ok, result}` and keeps the tool's own title, subtitle and `view`. The model's text and the stream's tool events are never shown. A write that ran is always the headline, so nobody repeats it. A complete run shows its last successful write (or else its last successful call) with that tool's subtitle. An unfinished run keeps that headline and gives the reason as the subtitle: the last tool error, then the crash message, then "The agent didn't finish". A declined task with no write is "Nothing was done" / "You cancelled it". `view` becomes the View button (`openTarget`: the event in Calendar, the screenshot file, the search URL). A turn that breaks with nothing done emits `error` ("Couldn't finish"); if anything succeeded it is `done`, so a sent message is never reported as a failure.
82. **"Complete" is decided in the main process and sent with Done.** A run is complete when nothing was declined, the last call worked, the last attempt of every write tool worked (so a send that failed on a name and then succeeded counts), and an agent turn ended with success. `AgentEvent.done` now carries `complete` (a shared-type change to the copied module). The card is styled from it: a green check and 4 s, or an X, 8 s and no "save as gesture" hint. Only a complete run is saved to recent tasks, offered first by New gesture, or compiled into a shortcut; on an unfinished run's Done card 3 fingers do nothing, since `optionsFor` lists only View and New command there. The renderer's old rule (ok when every evidence row is ok) showed a declined task, which has no evidence, as a success, and a successful retry as a failure. The mock agent now declines with the same "Nothing was done" / "You cancelled it".
83. **The renderer shows only the run on the card, and adopts a shortcut's runs.** The controller keeps `agentRun = { runId, intent, shortcut }` instead of a boolean, and drops events for any other run id; a stray `confirm` is declined so the agent never waits. A command's run is named only by `agentRun`'s reply. Its `started` usually arrives first, but so can another run's: main serialises runs, so a shortcut's agent fallback queued just before the command announces itself, and is then stopped by it. Taking the first `started` named the command after that fallback, showed its "Stopped" and left the real command running unseen with its confirms declined. So until the reply, every event is held; the reply's id then shows that run's events and drops the rest (declining their confirms). The card shows "Starting agent..." a moment longer, until the reply that follows `started`. A shortcut that needs the card, a compiled replay with a write step or the agent fallback after a failed replay step, emits its own `started`, so while `runShortcut` is pending those runs are adopted: Working, the steps and Confirm show as for a command. Their `done`, `error` or `stopped` opens no Done card, because `runShortcut`'s `ShortcutRunResult` is the authoritative result and becomes the toast (`ok` only when the whole task was done; "compiled · 1.2 s" for a replay). Read-only replays stay silent and show only the toast; in the smoke test a compiled one-step replay answered in about 0.15 s. A command started while a shortcut is still pending replaces it (main stops the shortcut, and a stopped replay never falls back to the agent; a fallback that had already started is stopped like any run), and its "Stopped" result is not toasted over the new Working card. A shortcut started from Settings › Test it replaces a command run the same way.
84. **Stop is immediate, but never hides a write.** A fist (or X) in Working shows "Stopped" at once and then calls `agentStop`; main emits `stopped`, resolves a pending confirm as Cancel, interrupts droid and drops the run's later events, and the session stays warm. Before, the toast waited for main's interrupt to return. A stop while the session is still starting cancels that start. A write that already ran, or was running at the stop (an AppleScript send can't be called back), still happened, so a stopped run that has a successful write sends one late `done` (`complete: false`) once its running tool settles, with that write as the headline and "You stopped the rest" (`Run.idle()` tracks running tool steps; the run's outcome doesn't wait for it, so a new command is never held up). The renderer remembers the run behind the Stopped toast: the toast becomes "Message sent" / "You stopped the rest", or, if the card has moved on, the notice "Message sent before you stopped". A stopped run with no write sends nothing more, and none is saved as a recent task.
85. **Claude's tool list is the real registry.** `src/main/claude/toolCatalog.ts` is gone: the intent prompt lists `TOOLS` (name and description of the 15 tools, including `contacts_find`), so intents name things the agent can actually do.
86. **Mac tools, as integrated (details in the module's own notes).**
    - Every tool's `run` returns a failed outcome instead of throwing, and the messages from `mac/` are written for the card. A missing macOS permission names its System Settings pane, and a missing Spotify key reads "Add SPOTIFY_CLIENT_ID to .env".

## Phase 8 — Custom gestures (shape shortcuts with compiled replay)

100. **A saved shape is recognition's static vector, matched with kNN like a letter.** No new module came from the scratch copy; the matcher and the recording check are a new pure module, `engine/gestures/customShapes.ts`, built on `staticFeatures` (hand-relative, left hands mirrored, so either hand works), `knn` and `euclidean`. A gesture's `shape` in `gestures.json` holds 10 vectors spread over the 1 s recording, rounded to 3 decimals. A hand matches when the k = 3 vote's nearest sample of the winning gesture is within 0.75. `gestureInput` builds the matcher from `store.gestures` and the camera's aspect, and rebuilds it when either changes, so a saved or deleted gesture takes effect at once. The built-in peace sign stays the engine's own rule (`builtin-peace`, no samples), and a custom shape outranks it.
    - **Calibration** (`customShapes.test.ts`, on recognition's synthetic signer, which varies hand size ±20%, tilt ±8° and finger curl ±0.06 between repetitions). One capture of A, L, I or Y is matched by 80–100% of later holds with the same hand (a hold counts when at least 80% of its frames match), about 80% with the other hand, and about 70% for a small, jittery hand. No other synthetic handshape comes within 1.0 of these captures. Letters use 0.7, but they have five recorded repetitions; a single 1 s capture covers less variation, so it gets a little more room.
    - **A resting hand must never run a shortcut.** A relaxed hand comes within 0.67 of a C and 0.8 of a CLAW. So loose shapes, where all four fingers are half bent, are refused when recording (101). This is the same rule the control gestures follow (6).
    - **A hand-edited `gestures.json` can't break it.** Main's `getGestures` drops entries that are not objects or have no string `id` and `task` (they can't run), and gives the rest a name (the id), a list of number vectors as `shape` (else `[]`) and a list of compiled steps (else none). The renderer still skips vectors that have the wrong length or a non-finite number. Before this, an entry without `shape` threw inside the store listener that rebuilds the matcher, and zustand passes that error on to `setApp`. Loading at launch, My gestures and every recording then failed, and a recording ended in a misleading "No hand seen".
    - **Shapes are read at launch, when My gestures opens, and after a save or delete.** Main reads the task and compiled steps from the file each time a shortcut runs. So a shape added to the file by hand takes effect only after My gestures is opened, or after a restart (TESTING Phase 8 says so).
101. **A recording is refused when it couldn't work as a shortcut, and the card says why.** `captureShape` takes the largest hand in each frame and checks, in this order:
    - **"No hand seen. Hold one hand up in view."** A hand must be in at least 60% of the frames, and in at least 8 of them.
    - **"Your hand moved. Hold the shape still."** The mean shapes of the recording's first, middle and last thirds must agree within 0.7. Still holds stay under 0.15, and under 0.65 for a small, jittery hand. Changing shape, or changing and coming back, gives 1.1 or more.
    - **"That reads as <a fist / a thumbs-up / an open palm / the peace sign / N fingers>, a control gesture. Try another shape."** This uses the gesture engine's own classifiers.
    - **"That looks like a resting hand. Make a clearer shape."**
    - **"Too close to “Gesture 2”. Try another shape."** The new shape is within the match distance of a saved one.
    - **"That reads as the letter Y. Try another shape."** Recognition's own letter classifier, with the user's taught letters and the current sensitivity, reads the new shape as a letter (a close call between two letters counts too). In Command mode a held letter waits out the longest control hold plus a grace period (about 1.25 s), so that a control gesture can drop it. A shape fires at 0.8 s, so a shape that is also a taught letter would run its shortcut while the user fingerspells, and the letter would be lost. Taught words are no rivals, because they move. The trade-off: a letter taught after a shape was saved isn't checked against it. Delete that gesture and record another shape.

    Each conflict counts when it shows in at least 30% of the frames. A shape that reads as a control that often would compete with it: far from the camera, an A reads as a fist in about a third of its frames, and in Ready a fist collapses the card.
102. **Recording, step by step.**
    - **Countdown.** The controller counts 3, 2, 1 with its own timers. Each tick replaces the `newGestureHold` page, and the ring in the feed's corner restarts.
    - **Recording.** At 0 the page is recording, and `app/shapeInput.ts` sends the next 1 s of camera frames to `captureShape`. The verdict goes to `controller.shapeCaptured`, once per recording. The mock hand's frames are never recorded.
    - **Timeout.** No frames means no verdict. After 2.5 s the controller refuses with "No hand seen…", or "The camera is off. Turn it on first." when the camera is off.
    - **Gestures while counting or recording.** Only swipe left (back) acts. The shape being formed may read as a fist, as with Teach › record letters (Phase 4). After a refusal, thumbs up records again, and a fist or swipe left goes back to the task list.
    - **A refusal is its own gesture screen** (`gestureScreen` returns `shapeRefused`). The refused shape, often a fist or a thumbs up, is usually still held when the reason appears, so it is spent and has to be made again. Otherwise a held thumbs up would retry, or a fist would leave, before the reason could be read. An engines test drives this with synthetic frames, and fails without the rule.
103. **Saving.** A new gesture gets the first free "Gesture N" name (the peace sign is gesture 1) and the id `gesture-<ms>`. It is appended to the list as read from the file, not from the store, because the main process may have compiled another gesture into the file meanwhile. The store follows the file, and the toast "Gesture saved" / "Gesture 2 · <task>" leads to My gestures, where it is listed. The toast leads there rather than to Ready on purpose: shapes act only in Ready and Collapsed, so a hand still holding the new shape can't fire it straight away. A failed save keeps the page, with "Couldn't save it: …" as the reason. The Phase 1 "Saved" check over the feed (`captured`) is gone, because the toast is the confirmation.
104. **Sign a new task.** The last option of New gesture goes to Ready with the hint "Sign the task for your gesture", in Command mode. If the card was in Dictation or Spell mode, it switches like a swipe does: the header flashes and the mode is saved. Without the switch, Dictation would type the signs into the focused app. The phrase is signed and proceeded as usual. On proceed, the task is Claude's intent, else Claude's cleaned-up sentence, else the signed sentence, with a quick-menu pick as its prefix. The card then goes to recording instead of Did you mean, Agent ready or the agent. Without `ANTHROPIC_API_KEY` the signed sentence is the task, with the usual "Add ANTHROPIC_API_KEY to .env" notice. The request lasts as long as the phrase: a cancel, collapse, mode switch or Settings ends it, as it ends a quick-menu pick.

A saved shape held 0.8 s in Ready or Collapsed calls `runShortcut` (main `agent/shortcuts.ts`). A compiled replay runs with no model and shows a toast with "compiled · 0.4 s", using the real duration. The first run, or a run after a failed replay step, goes through the agent, whose Working and Confirm cards the card adopts (83). A complete run is compiled. Swipes page through the list, and the page dots are shared with Teach a sign (`PageDots` moved to `SettingsFrame`). Leaving a gesture's detail returns to its page. ## Gemini provider

122. **`LLM_PROVIDER` picks the model behind both LLM calls: `claude`, `gemini`, `local` or `mock`.**
    - Unset or blank means `claude`, so nothing changes for a `.env` without it.
    - The value is trimmed and case-insensitive. Main reads it once at launch, after `loadEnv()`, so `.env` works.
    - Any other value makes both calls answer `Unknown LLM_PROVIDER "x": use claude, gemini, local or mock`, and launch logs `[llm] Unknown LLM_PROVIDER …`. The app still runs, and nothing falls back to another provider.
123. **One provider serves intent and spelling, with the same prompts and schemas as Claude.** With `LLM_PROVIDER=gemini`, fastASL needs no Anthropic key.
    - `interpretWith` and `spellSuggestWith` run on any provider, and `createLlmService` (`src/main/llm`) wires them up.
    - The prompts (`INSTRUCTIONS`, `buildSystemPrompt`, `buildRequest`, the spelling `SYSTEM` and `buildSpellRequest`), the zod schemas (`IntentReply`, `SpellReply`, now exported) and `sanitizeIntent` stay in `src/main/claude`. The Claude path and its tests didn't move.
    - Output caps: Claude keeps 1024 for intent and 512 for spelling. Gemini and local use 300 for both, as the user asked for about 300.
    - `createClaudeService` is now `createLlmService` on `claude`.
124. **The corrective retry and validation are shared; each provider brings a transport.**
    - `askStructured(transport, req)` in `src/main/llm/structured.ts` runs the exchange: one call, then exactly one corrective retry when the reply fails to parse or validate. Both attempts share one deadline signal, and zod checks the result.
    - A transport supplies:
      - `send`
      - `text`, which reports a cut-off reply before parsing
      - `echo`, the bad reply as a turn, or none when it is empty
      - `failure`, the error mapping
      - its name for "<name> took too long to answer" and "<name> returned an unusable reply (…)"
      - its deadline
    - Claude's `askJson` is this exchange with the Claude transport. It sends the same request, keeps the same 15 s deadline and the same messages, and its 52 tests pass unchanged.
125. **The Gemini client uses `@google/genai` 2.31.0.**
    - **Version.** Pinned exactly and kept in `dependencies`, so electron-vite leaves it external. Its engines field is `>=20`, and its README says 3.0 will need Node 22.
    - **Built lazily, never without a key.** `getGemini()` builds the client on first use, the same way `getClaude` does, and rebuilds it only when the key changes. Without a key the SDK would fall back to Google Cloud default credentials and probe the metadata server, so it is never built without one.
    - **Missing key.** The result is `{ ok: false, error: 'Add GEMINI_API_KEY to .env', missingKey: 'GEMINI_API_KEY' }`.
    - **Client options.** `vertexai: false` pins the Developer API. `httpOptions.retryOptions.attempts: 1` keeps the SDK from retrying: 2.31.0 doesn't by default, and this keeps it that way.
    - **One call per request.** `automaticContinuation: false` makes each `generateContent` one HTTP request.
126. **The default `GEMINI_MODEL` is `gemini-3.5-flash-lite`.** The docs and the user's wording differ here, and the docs win.
    - **What the user asked.** "A current Gemini Flash model".
    - **What the docs say.** "For any new projects, use our latest models: 3.5 Flash-Lite or 3.8 Flash". Flash-Lite is in the Flash family, is stable, and is on the free tier.
    - **3.8 Flash.** It never answered on this free-tier key during the research probe: it timed out at 20, 60 and 40 s, and 3.6 Flash returned 503.
    - **3.5 Flash-Lite.** It answered every live check here in 2.5 to 6.6 s. Once, the free tier answered with a 5xx, shown as "Gemini is busy right now".
    - **Switching.** `GEMINI_MODEL=gemini-3.8-flash` picks the bigger model, and the thinking setting and output cap follow the model (128). It is unverified: it still timed out after 15 s at review time.
127. **Structured output uses `responseMimeType: 'application/json'` and a `responseSchema` built from the same zod schema that validates the reply.**
    - **How.** `geminiSchema()` converts the schema's JSON Schema into Gemini's `Schema`, using the `Type` enum. `intent` is written as `nullable: true`, every field is `required`, and `propertyOrdering` follows the fields. A test pins the exact intent and spelling schemas.
    - **Unsupported shapes.** A shape the converter can't express throws, rather than sending a looser schema.
    - **Not `z.toJSONSchema` as-is.** Its `$schema` key makes the SDK move the schema to `responseJsonSchema`, and the SDK's converter drops `additionalProperties`.
    - **Still validated.** The reply is validated with zod and sanitized like Claude's, because the docs say the model "ignores unsupported properties".
128. **Thinking stays minimal, and the 300 tokens are for the answer.** `maxOutputTokens` includes thought tokens, so `thinkingFor(model)` sends:
    - `MINIMAL` for Flash-Lite
    - `LOW` for other 3.x and 4 models (3.8 Flash rejects `MINIMAL`)
    - `thinkingBudget: 0` for 2.5, and 128 for 2.5 Pro, which can't turn thinking off
    - nothing for 2.0 and 1.x

    Only one of the two fields is ever sent, because both together is a 400. No temperature or top-p is sent either, following the Gemini 3 guidance. A `models/` prefix on `GEMINI_MODEL` is ignored when matching.

    Thinking the model can't turn off gets room on top of the 300 (`thinkingAllowance`), so it can't cut the JSON off: 1024 tokens for `LOW` and 128 for 2.5 Pro. `MINIMAL`, `thinkingBudget: 0` and no thinking get none, so the default model sends exactly 300. It used 0 thought tokens live.
129. **How a Gemini reply is read.**
    - **Text.** The text is the first candidate's non-thought parts.
    - **Corrective retry.** A cut-off reply (`MAX_TOKENS`) gets the corrective retry with "cut off; keep it shorter", and any other non-STOP finish gets it with "it stopped early". The bad model turn is echoed back unchanged, thought signature included, unless it has no text.
    - **Blocks.** A blocked prompt (`promptFeedback.blockReason`) or a SAFETY-class finish is "Gemini declined to answer this one", with no retry, like a Claude refusal.
    - **Errors.**
      - "Gemini rejected GEMINI_API_KEY. Check .env": a 400 about the key, a 401 or a 403. `missingKey` is not set, because the key is present.
      - `Gemini has no model "<id>". Check GEMINI_MODEL in .env`: a 404.
      - "Gemini is busy right now. Try again in a moment": 5xx.
      - "Can't reach Gemini. Check your connection": `fetch failed`.
      - "Gemini took too long to answer": a timeout.
      - `Gemini error: <message>`: anything else, cut to 160 characters.
130. **HTTP 429 is retried up to 3 times, with a status in the card, but only when a retry can work.**
    - **Status line.** Before each wait, the call reports "Rate limited, retrying...".
    - **Waits.** What the server asked for, or else 1 s, 2 s and 4 s with ±10% jitter. Live against a stub, the backoff gaps were 1.1, 1.9 and 4.2 s.
      - The server's delay is the longer of `RetryInfo.retryDelay` and the message's "Please retry in 37.4s", because `RetryInfo` is often cut to whole seconds.
    - **One budget per exchange.** The first attempt and the corrective retry share the 3 retries, so one call shows the status at most 3 times.
    - **No retry when it can't help.** The error then comes at once, with no status:
      - **Wait too long.** A wait that would leave less than 5 s before the 30 s deadline. A free-tier per-minute 429 often asks for 20 to 50 s, and retrying sooner only earns another 429. Waits that fit are honored in full, up to about 25 s.
      - **Daily quota.** A `QuotaFailure` whose `quotaId` is per day. It resets at midnight Pacific.
      - **Zero quota.** A quota of 0 (`quotaValue` "0", or "limit: 0"): the model isn't on the key's tier.
    - **Messages.**
      - "Gemini is rate limited. Try again in 51 s", with the server's delay. "…in a minute" when the server sent none.
      - "Gemini's daily quota is used up. Try tomorrow or set LLM_PROVIDER=claude".
      - "Gemini has no quota for <model> on this key. Change GEMINI_MODEL in .env".
    - **Only 429.** 503 and other 5xx get "busy" at once, since the user asked for retries on 429.
    - **Deadlines.**
      - Each HTTP request gets 15 s, so a stalled model (like 3.8 Flash in 126) fails as fast as a whole Claude exchange.
      - The whole Gemini exchange gets 30 s: the requests, the waits and the corrective retry.
      - A wait still running at the deadline is cut short. Claude keeps its 15 s.
131. **The status reaches the card over a new IPC channel, `llm:status`, and the card can cancel a call over `llm:cancel`.**
    - `interpret` and `spellSuggest` take an optional `callId`. Main broadcasts `{ callId, status }` to live windows on `IPC.llmStatus`, the same way agent events go out.
    - `ipcServices` gives each call an id (a random per-window prefix plus a counter), passes only that id's events to the call's listener, and unsubscribes when the call settles. A call with neither a listener nor a cancel signal gets no id, and main then gives the provider no `onStatus` and no signal.
    - `Services.interpret` and `spellSuggest` take an optional `onStatus` and an optional `AbortSignal`, which the mock services ignore.
    - **Cancelling.** When the signal aborts, `ipcServices` sends `llm:cancel` with the call's id. Main keeps an `AbortController` per running call id and aborts it. A call dropped before it reached main is never sent.
      - In main the signal reaches `askStructured`, which links it to the deadline. The in-flight request and any rate-limit wait stop at once, and the call answers "Cancelled", which nobody shows.
      - Without this, a call the card had dropped kept retrying 429s for up to 30 s. Every edit during a rate limit added another chain of requests against the same per-minute quota.
      - It applies to every provider. A superseded Claude or Ollama call stops too, and the card never used those answers anyway.
    - The dev log prints `[gemini] interpret status: Rate limited, retrying...`, and `-> {"error":"Cancelled"}` for a cancelled call. Each call's line is tagged with the provider (`[claude]`, `[gemini]`, …), so the Claude lines in TESTING Phase 5 read as before.
132. **The status notice stays as long as its call does, and only on its own.** It is handled by the controller's `showLlmStatus` and `clearLlmStatus`.
    - **When it shows.** Only while the call is still the card's: the pending interpretation is still that call, or the spelling list is still pending. The notice line must be empty, already hold this status, or hold the last LLM error. So it never covers another notice, such as a missing key or "Still typing the last pick", but a new call's status takes the place of "Gemini is rate limited…" from the call before.
    - **When it goes.** As soon as the call settles. It also goes as soon as the call is superseded or cancelled: an edit, a new sign (an ambiguous-sign pick included), a delete, a quick-menu pick, a fist, a collapse or Settings. Every `setView` or change of the pending interpretation drops a stale status and cancels the stale call (131).
    - **A superseded call.** Its late status lines are ignored.
    - **Never clears another notice.** A notice that replaced the status meanwhile stays when the call settles.
    - **The final error.** It goes through `notify` as before when the card proceeds. When the Sentence card showed "Rate limited, retrying..." and the retries then fail, the error replaces the status at once, without waiting for a thumbs-up, so the card never looks as if the call worked.     - **Where it shows.** On the Sentence card (also during "Understanding..."), on the spelling list and in the collapsed pill.
    - **Tests.** Two existing controller assertions now also expect the status-listener and cancel-signal arguments (`expect.any(Function)`, `expect.any(AbortSignal)`).

## Real-camera tuning of teaching and word recognition

139. **Teaching and word matching are now tuned on a real camera, not only the synthetic signer.** On the MacBook camera (1280x720, ~17-30 fps) one signer's HELLO never got past "1 of 10". Dev logs of each repetition's DTW distances showed why:
    - **Clean repetitions disagree more than synthetic ones.** Repetitions with the hand already up, ending in a hold, sat 1.57-1.81 from their nearest neighbour. That is above the 1.5 that both teaching (agreement) and recognition (accept) used, so no second repetition was ever kept. Recognition would also have rejected the sign after teaching.
    - **Raises are farther away.** Repetitions that included raising the hand into view sat 2.15-3.4 from the clean ones.
    - **The stall was silent.** A repetition that matched nothing replaced the last one as "the newest of two loners", so the count stayed at 1 with no message.

    What changed:
    - **5 repetitions per word** instead of 10 (letters stay 5). The controller's TEACH_REPS and TeachSession's default both changed.
    - **Teaching agreement.** Two clean repetitions agree within 2.0 (WORD_AGREEMENT in teach.ts). A link involving a raise or lowering must still be within the strict 1.5. Otherwise the raise joins the kept set, and raising the hands later reads as the sign; the synthetic "rising and falling" test catches exactly that.
    - **"Didn't match" is said.** A clean repetition that agrees with no earlier clean one gets "That one didn't match the others. Try again." instead of silently replacing it.
    - **"Too short" is silent.** A too-short movement is the hand getting back into position between repetitions, and on a real camera that message showed after nearly every repetition. "Too long" still shows.
    - **Per-word accept radius in the recognizer.** A word's radius is 1.4 x the median distance from each of its templates to its nearest other template, clamped to [1.5, 2.4]. Sensitivity still scales it.
      - Synthetic words (median ~0.5) keep 1.5, so the calibration tests are unchanged.
      - A word recorded on a noisy camera gets room without widening every other word.
      - A fixed 2.2 was tried first, and a test showed an open-palm swipe being swallowed as a word.
    - **Measured after the change.** Teaching HELLO with the hand kept up between repetitions completed 5/5 at the first try, with repetitions 0.68-1.93 apart (radius 1.5). In Dictation, HELLO matched at 0.91 and became "hello", and Gemini answered "Hello." with Insert text / More options. Other movements (swipes, reaching, scratching) sat at 2.99-8.9. One attempt at 1.62 was rejected; it is unknown whether it was a HELLO.
    - **Dev diagnostics.** `[teach-dbg]` logs each repetition's frames, duration, entered/left, hand slots and distances to the earlier ones. `[sign-dbg]` logs each movement's nearest word, its distance and that word's radius.

## Guess, confirm, learn

140. **A sign the app doesn't know is guessed on the first try, confirmed by hand, and learned from that one movement.** When a whole, clean movement matches no taught word, a vision-capable LLM looks at a few camera frames and a summary of the hand tracking and names up to 3 signs. The card asks "Is this HELLO?". A pick adds the word to the phrase, as a recognized sign would, and saves that movement as one more `SignTemplate`, so the next one is recognized locally, with no call. A fist learns nothing. Nothing about the vocabulary is hardcoded: the model names the sign, the user confirms it. Settings › Teach a sign gets the same flow as its first option, "Show me a sign" (150).

141. **Feasibility was checked first, on real dictionary clips, before any UI was built.** 25 live API requests in all: 24 `generateContent` calls and one model list. The key was read from `.env` and never printed.
    - **Clips.** 11 short public clips from signasl.org: HELLO, THANK YOU, YES, PLEASE and MUSIC (StartASL); NO (Elemental ASL Concepts); EMAIL (Marie Katzenbach School); PLAY, HELP, WATER and MORE (ASLbricks). They were kept in the session scratchpad, and nothing in them was run.
    - **Method.** A headless Electron harness ran each clip through the app's own MediaPipe tracker, segmenter, frame ring (288 px JPEG at 8 fps) and motion summary, then sent the request through the shipped `identifySign` prompt and Gemini transport. The clips start and end with the hands down, which the app never guesses (146). So the movement was taken as the span where a hand is at least 1.5 hand lengths above its resting height, by the same rule for every clip. Each request carried 7–8 frames.
    - **`gemini-3.5-flash-lite`** (the intent default): 10 of 11 answered (one 5xx). Top-1 **0/10**, top-3 **0/10**. It answered CURIOUS for EMAIL, SUPPORT for HELP, NICE for MUSIC and THANK YOU, FINE for PLEASE and CALIFORNIA for PLAY, and called NO and WATER "not a sign". Latency 4.1–10.1 s, median 6.4 s. For signs, that is chance level.
    - **`gemini-3.8-flash`**: the one call answered 5xx.
    - **`gemini-3.5-flash`**: 7 of 12 answered. Top-1 **5/7** and top-3 **5/7**: HELLO (0.95), THANK YOU (0.95), PLEASE (0.98), HELP (0.98) and MORE (0.95) were right; EMAIL (SITUATION) and NO (DIRTY) were wrong. Latency 1.7–7.5 s, median 3.4 s. The other 5 calls failed: 4 were rate limited ("Try again in 50–60 s", the free per-minute quota, after about 5 calls in a minute) and 1 got a 5xx. YES, WATER, MUSIC and PLAY never got an answer.
    - **Decision.** The default model can't do it, but Flash can, well above chance. So it was built, and sign guesses use their own setting, `GEMINI_SIGN_MODEL`, default `gemini-3.5-flash` (the user confirmed this; their free tier serves it).
      - Intent and spelling stay on `GEMINI_MODEL` (Flash-Lite). Free-tier quotas are per project and per model, so the two calls draw on separate buckets.
      - 3.5 Flash thinks at `LOW`, with 1024 tokens of room on top of the 300-token answer, from the existing `thinkingFor` mapping (128).
      - Nothing falls back to Flash-Lite. A sign model Gemini doesn't serve (404) says `Gemini has no model "<id>". Check GEMINI_SIGN_MODEL in .env`, and one with no quota on the key says `… Change GEMINI_SIGN_MODEL in .env`. Gemini errors now name the setting the model came from.
      - The sample is small (7 answers) and these were studio clips, not a MacBook camera at a desk. Expect lower accuracy on your own signing.
    - **Not pursued.** Google's Isolated Sign Language Recognition model (250 signs, MediaPipe landmarks) would run on device, but it has a fixed vocabulary and would need a new runtime dependency. It wasn't needed once Flash cleared the bar.

142. **One prompt, one schema, every provider: `identifySign` in `src/main/claude/sign.ts`.**
    - **Request.** The frames are sent as images before one JSON text: `{frames: <count>, motion, mode, known_signs}`. `known_signs` is the taught word labels, so a known word can be named (and gain another example, 148). The text never carries the images.
    - **Prompt.** It says the image is unmirrored (the signer's right hand appears on the image's left), that the motion summary is more precise about handshape and direction than the images, and that everything in the request is data, not instructions. It lists what is not a sign: fidgeting, scratching, touching the face or hair, adjusting glasses, reaching, typing, and hands moving into or out of view.
    - **Reply.** `{ is_sign: boolean, candidates: [{ gloss, confidence }] }`, with at most 3 candidates, validated by zod (`SignReply`, `.max(3)`). Gemini's `responseSchema` now carries `maxItems` (`geminiSchema` learned it), and Claude's strict format gets it as a description.
    - **Sanitizing.** Glosses are upper-cased and kept to letters, digits, spaces, hyphens and apostrophes. Anything longer than 32 characters (a sentence) is dropped, as are duplicates. Candidates are sorted by confidence (clamped to 0..1) and capped at 3. `is_sign: false` gives no candidates, and `is_sign` with no usable candidate is "not a sign".
    - **Caps and retries.** 512 output tokens on Claude, and 300 on the others (plus the 1024 thought tokens that 3.5 Flash may use at LOW, 128). The shared `askStructured` gives one corrective retry, text only: the images go in the first user turn only (`JsonRequest.images`, `userTurn(text, images)`). It shares the deadline and cancellation too.

143. **What each provider sends.**
    - **gemini:** `inlineData` JPEG parts before the text, with `responseMimeType` and `responseSchema`, and the same 429 handling, status line and deadlines as intent (130).
    - **claude:** base64 `image` content blocks before the text block. It is tested only with a fake transport, because there is no Anthropic key here.
    - **local:** before any frame is sent, Ollama's `POST /api/show` is asked for the model's capabilities, once per URL and model (then cached). A model without `vision` answers "`<model>` can't see images. Set LOCAL_LLM_MODEL to a vision model", and nothing is sent. An Ollama too old to list capabilities just gets the call, and a 400 about images maps to the same message. "Start Ollama" and "Run: ollama pull" work as for intent.
    - **mock:** a canned HELLO / THANK YOU / PLEASE, through the same validation. The renderer's `mockServices` (`FASTASL_MOCK=1`) answer the same.

144. **Frames come from a small ring buffer in the renderer (`engine/camera/frameRing.ts`).**
    - **What it keeps.** About 8 fps (one per 125 ms) of the tracked camera frames, drawn to a reused 288 px-wide canvas at the camera's aspect and stored as JPEG (quality 0.7, about 4–10 KB). Only the last 4 s are kept. A frame in between is never drawn. Each frame keeps the tracker's timestamp, so it lines up with the movement's landmarks.
    - **When it runs.** `engines.ts` feeds it only while `controller.wantsSignFrames()` holds: a provider that looks at frames, with its key, on a card where a guess can start or on Show me a sign. Elsewhere the ring is empty and costs nothing. Encoding one frame takes about a millisecond, inside the frame callback.
    - **Picking.** `pickFrames` spreads up to 8 frames evenly over [movement start − 100 ms, end + 100 ms], always keeping the first and the last. A short movement or a slow camera widens the window, 100 ms at a time up to 400 ms each side, until it holds 6.

145. **The motion summary (`engine/recognition/motionSummary.ts`) says what the frames blur.**
    - **Contents.** The duration, then one hand or two. For each hand: the side it is on (the signer's own), its height in the frame, and its handshape at the start and the end (a majority over 3 frames, per digit, from `analyzeHand`), named with the ASL shape it resembles ("thumb and pinky extended (Y)"). Then how it moved: the direction of its farthest point from the start, in the signer's terms ("toward the signer's right and down"), the distance in hand lengths, "then back" when it returns, "in a circle", "repeated: 4 strokes up and down", and toward or away from the camera when the hand's size changes by 20%. With two hands, it also says whether they come together or move apart.
    - **Hands are followed by position, not by label.** MediaPipe's Left/Right flickers (40), and a flicker split one hand into two in the first version of the summary. A hand more than 2.5 hand lengths from the only tracked hand, within 200 ms, is the second hand.
    - **Example**, measured live from a dictionary HELLO: "0.4 s, one hand, on the signer's right, high in the frame. Hand: flat hand, four fingers extended (B) throughout. Moves toward the signer's right 0.8 hand lengths."

146. **Only sign-like movements are guessed.** All of these must hold:
    - The local recognizer rejected it. `RecognitionSession.rejectedMovement` holds the movement behind that one `rejected` event. A cancel (too short or too long) has none.
    - It is clean: not `entered` and not `left`, so it is not a raise or a lowering of the hands.
    - It lasted 400–3000 ms (`signLike`).
    - It is not a control gesture, nor the movement into one, nor what follows one:
      - A movement that made a swipe is never guessed. If the swipe is judged in time, the swipe acts; if too late, nothing happens, as before.
      - A movement that starts within 1.5 s of a control gesture acting is its follow-through (a swipe's return stroke, the hand coming down from a pick), so it is never guessed (`GUESS_AFTER_GESTURE_MS`).
      - The guess waits `GUESS_WAIT_MS` after the movement ends: the longest control hold (1 s) plus 250 ms, times the sensitivity's hold scale. That is about 1.25 s at medium, measured in camera-frame time. A control gesture held with the movement's last shape (moving into a fist, a thumbs up or a finger count) fires within it, and a letter held with that shape arrives within it. Either one drops the guess, as does any recognized sign, a new screen, or the camera going away.
    - An LLM is available: `Services.signGuessUnavailable()` is null. That needs a known provider with its key (`local` and `mock` need none).
    - No guess is in flight, the last one started at least 3 s ago, and the card is Ready, Listening, Recognizing, Building, Sentence (not while it proceeds) or Dictation. Spell mode never guesses.

    A movement that fails any of these is rejected as before, with no call and no frames sent. Letters keep working as they did: a hand that rests in a taught letter's shape after an unknown movement gives the letter, and nothing is asked. The cost is about 1.25 s added to a guess, on top of the model's 2–7 s.

147. **While the guess runs, the phrase carries on.** Listening ends as for any rejected movement, and "Identifying sign..." shows through the existing notice (`showLlmStatus`), which a rate-limit status replaces. The guess is superseded, and cancelled in main over `llm:cancel`, by anything that moves the phrase on:
    - a sign recognized meanwhile
    - an edit or a delete
    - a mode switch or a reset
    - a control gesture that leaves the phrase (quick menu, collapse, Settings)

    Hands moving on (Listening and back) don't cancel it, and neither does ending the phrase with both hands down. When the answer comes on the Sentence card, a pick adds the word and goes back to the Sentence card with it (and asks for a new interpretation). When it comes during a new movement, the list replaces Listening, and "no" goes back to Ready.

148. **"Is this HELLO?" is the existing Did you mean list with a new purpose, `learn`.**
    - **The list.** Its heading is "Is this <first gloss>?", followed by the up to 3 options. The hint reads "hold up 1–3 fingers · thumbs up = 1 · fist = no". It is a new screen for the gesture engine, so a shape still held from the sign can't pick.
    - **A pick** puts the card back where it was, then adds the word as a recognized sign does: in Ready it becomes "Recognizing" with the word, in a phrase it joins the strip, and in Dictation it is typed. It also saves `wordTemplate(gloss, features)`: the segment's frame vectors, resampled to 32 frames and rounded to 3 decimals, exactly as `TeachSession.finish` makes each repetition (a test compares the two).
    - **Saving.** It goes through the same merge-and-save as `teachLearned` (`addTemplates`). The store updates, so recognition reloads at once. A word already taught gets this movement as one more template, which helps exactly where matching had failed. A notice "Learned HELLO" stands in for the toast, which would interrupt the phrase.
    - **No.** A fist, the X or Edit learns nothing and goes back to the phrase as it was.

149. **When a guess fails, the movement stays rejected, as before.** A missing key, a rate limit or no network gives the error as a notice, at most once a minute, so it doesn't nag. "Not a sign" is silent. A bridge that throws (a renderer hot-reloaded onto an older preload) counts as a failed guess, never a stuck one. `ipcServices` reports "Restart fastASL to guess signs" when the preload has no `identifySign`. `controller.dispose()` cancels a guess in flight.

150. **Settings › Teach a sign › Show me a sign.**
    - **The list.** Row 1 of every page is "Show me a sign". The list shows 3 signs per page (it was 4), so that with "Spell a new word" every page still has 5 rows, picked by 1 to 5 fingers. There are now 14 pages. List-based teaching itself didn't change.
    - **The page.** It waits for one clean repetition ("Waiting for a sign", then "Listening..."). It asks `identifySign`, showing a spinner and "Identifying sign...". Then it shows "Is this HELLO?" with the guesses and "None of these: pick from list". Fingers or thumbs up (option 1) pick.

    - **Settling.** Movements that start within 1 s of the page listening are ignored. This is decided once, when the movement starts. That is the hand coming down from the finger pick that opened it, and asking about it would block the real sign. Raises, lowerings and movements that are too short are ignored silently. "Too long" and "That didn't look like a sign. Try again." are said, as is the LLM's error. Without an LLM, the page says what to add ("Add GEMINI_API_KEY to .env") and sends nothing.

## Live-testing fixes (Listening, moving on, the other hand)

155. **"Listening..." is a header status, not a card.** A movement used to switch the card to the Listening layout (feed + bars) and back again when it turned out to be no sign. The two layouts differ in height, so the window resized on almost every movement, which read as flashing. Now `controller.signStart` only sets `store.signing`, and the header shows "● Listening..." over the current card (Ready, Recognizing, Building, Sentence, Dictation). The card changes only when a sign arrives. recognitionInput debounces it by camera-frame time: it shows after a movement has lasted 400 ms and stays at least 700 ms, so twitches never show it and it doesn't blink.
156. **"Identifying sign..." moved to the header too.** It was a Notice row that came and went, which also resized the card. Notice now skips that one text, and the header shows "Identifying..." while a guess is in flight.
157. **A sign after a finished sentence starts the next phrase.** On the Sentence card, a recognized sign (or a confirmed guess) clears the old words and starts a new phrase (`startNextPhrase`), keeping only a quick-menu prefix or gesture task. Before, it was appended to the sentence, so the card seemed stuck on the old words. Hands down between words still ends the phrase, as before.
158. **Only the hands a word uses are compared.** Each word template knows its hand slots (present in at least half its frames). When matching, the query's other hand is left out if it moved less than 40% of the busiest hand: resting or wandering in view. One that moves like a signing hand still counts, so a two-handed movement can't pass as a one-handed word. The synthetic "two-hand swing" unknown caught the first version, which ignored every extra hand. Slot-cut template frames are cached per slot set, because recutting them per query pushed the calibration tests past their timeout.
159. **Confirmed guesses learn only the signing hand of a one-handed sign.** identifySign's candidates now carry `hands` (1 or 2, how many hands the sign uses in standard ASL), in every provider's schema. For a one-handed sign, the saved template keeps only the user's dominant hand: the slot most of their one-handed word templates use. With no history it keeps the hand that moved more. Motion alone picked the wrong hand on a real THANK YOU, because the other hand was being lowered and moved more. That saved THANK YOU was cleaned the same way (backup kept outside the repo).
160. **Wider per-word radius, and one for single templates.** radiusScale went from 1.4 to 2.4. The real HELLO templates' median nearest distance was ~0.8 (radius ~1.9), and the signer's later HELLOs landed at 0.91-2.2, while other movements landed at 2.5-8.9. A word with one template (one confirmed guess) has no spread to measure, so it gets `singleTemplateRadius` 2.0. A real one-shot THANK YOU then matched at 1.88-1.89. Synthetic words keep the 1.5 floor.
161. **Swipes need a quick sweep.** A slow sideways fist (1.8 hand lengths over 1.2 s) is not a swipe (≥ 0.22 frame widths within 300 ms), so it went to identifySign as an unknown movement. Thumbs up continues on the Sentence card as well.


## Pretrained sign model

162. **Signs are recognized out of the box by a pretrained model; teaching is optional now.** The Kaggle "asl-signs" 1st-place model (hoyso48, 250 signs, MediaPipe landmarks in) runs in the app on every movement. The user's taught signs and the LLM guess still come after it (171).
    - **Source and licence.** The weights are from https://huggingface.co/sign/kaggle-asl-signs-1st-place (`model.tflite` and `sign_to_prediction_index_map.json`), MIT per that model card. The original solution is https://github.com/hoyso48/Google---Isolated-Sign-Language-Recognition-1st-place-solution, which has no licence file of its own. `src/renderer/public/models/MODEL_LICENSE.md` has the attribution and the MIT text.
    - **Conversion.** tf2onnx 1.17.0, opset 17; its outputs match the TFLite model's. Every one of its 5,490,414 weights is exactly representable in float16, so `scripts/models/fp16-weights.py` stores them as float16 with a Cast back to float32. The outputs are bit-identical (all 988 held-out inputs in 170 give the same probabilities), the file is 11.2 MB instead of 22.2 MB, and it loads in about 200 ms instead of 355 ms. It is committed as `src/renderer/public/models/islr1st.onnx`, and the label map as `engine/model/islrLabels.json`.

163. **Microsoft's ASL Citizen ST-GCN adds the words the Kaggle model lacks, and is never committed.** It knows 2731 signs, including HELP, MORE, EMAIL, MAIL, SEND, MUSIC, PLAY, MEETING, STOP and WHAT (neither model has SPOTIFY).
    - **Licence.** The ASL Citizen licence is non-commercial research only, with no redistribution. So neither the weights nor anything derived from them (the ONNX, the label list) is in the repo. `src/renderer/public/models/asl-citizen/` is gitignored.
    - **`npm run setup:citizen`** (`scripts/setup-asl-citizen.mjs`) downloads only what it needs and prints the expected size first. That is the official weights zip (28.9 MB, https://github.com/microsoft/ASL-citizen-code/releases/tag/checkpoints_v1, SHA-256 pinned), plus `ASL_Citizen/splits/train.csv` out of the 45.9 GB dataset zip by HTTP range requests: its end records, the first 64 KB of the central directory, and the 0.8 MB member. That comes to 29.75 MB in all. The class order is the sorted unique glosses of train.csv (2731).
    - **The conversion runs in Node, with no PyTorch or Python.** `scripts/asl-citizen/` reads the zip, unpickles the checkpoint (a fixed allowlist of globals, so a tampered file can't run code), and writes the ONNX graph of our own re-implementation of the OpenHands ST-GCN (MIT). It matches a torch export of the same network within 9.2e-5 on the logits (which are about 200 in magnitude), with argmax agreeing 15/15. Conversion takes about 0.4 s. `--weights` and `--labels` take local copies.
    - **Without it the app works as before plus the Kaggle model.** The log says `[model] ASL Citizen model not installed (npm run setup:citizen): using the Kaggle model only`. Vite copies `public/` into builds, so a build made on a machine with it installed contains it and must not be distributed.

164. **Runtime: onnxruntime-web 1.30.0, wasm, one thread, in a Web Worker.**
    - One thread needs no SharedArrayBuffer, so the page needs no cross-origin isolation. The CSP already had `'wasm-unsafe-eval'`, `worker-src 'self'` and `connect-src 'self'`; nothing changed there.
    - `engine/model/model.worker.ts` holds the sessions, so inference never blocks the camera loop or the card. If the worker can't start, the sessions run on the page (`[model] worker unavailable, running on the page`).
    - The renderer aliases `onnxruntime-web/wasm` to its `ort.wasm.min.mjs` build, which loads `ort-wasm-simd-threaded.{mjs,wasm}` from `ort.env.wasm.wasmPaths`. `scripts/fetch-assets.mjs` copies those two files from node_modules into `public/ort/` (gitignored), as `npm install` / `npm run setup` already did for MediaPipe. The default build names the wasm with `new URL(…, import.meta.url)`, so Vite copied another 14 MB into every build.
    - **Measured in the built app** (file://, a 640x360 MJPEG stream). Both models load in 435 ms in the worker. A Kaggle answer takes 16–71 ms (two runs plus messaging), and an ASL Citizen one 360–385 ms (both hand assignments in one batch of 2). The camera stays at 30–35 fps throughout. In Node, one Kaggle run on a 40–90-frame movement takes 16–30 ms.

165. **Input and hand slots.**
    - **Kaggle model.** `[T, 543, 3]`, raw (unmirrored) x, y, z, NaN where missing. FaceLandmarker's first 468 of 478 points fill 0–467. The pose (489–521) stays NaN, because the model doesn't use it. The signer's left hand fills 468–488 and their right hand 522–542 (`engine/model/inputs.ts`).
    - **Which hand goes where.** HandLandmarker's labels assume a mirrored image, and the camera pipeline feeds raw frames, so the hand labelled 'Left' is the signer's right hand. Two hands with the same label are told apart by position: the one on the image's left is the signer's right.
    - **Safety net.** Swapped slots drop the Kaggle model to 0.5%. So both assignments run and the more confident answer wins. The research measured no accuracy lost to this on held-out data.
    - **ASL Citizen.** `[2, 128, 27]`: nose, eyes, shoulders and elbows from PoseLandmarker, and per hand the wrist, thumb tip and each finger's base and tip. Missing points are 0. The input is padded or stepped to 128 frames and normalized by the mean shoulder centre and width over all 128 frames, the zero padding included, exactly as ASL Citizen's dataset code does.

166. **The face and the body pose are tracked only for the model, on alternating frames.**
    - FaceLandmarker (`face_landmarker.task`, float16, 3.8 MB) and PoseLandmarker lite (`pose_landmarker_lite.task`, 5.8 MB) are downloaded by `fetch-assets.mjs` into `public/mediapipe/`. Each loads the first time it is asked for, with the hands' delegate (GPU).
    - **Where.** The camera tracks them only once the model has loaded, on cards where it can be asked: views that take signs outside Spell mode, and Show me a sign. Elsewhere (collapsed, menus, the agent) they cost nothing. The pose is tracked only when ASL Citizen is installed.
    - **Measured in the built app** (640x360): hands 13–17 ms, face 6–11 ms and pose 9–11 ms per call. Running both every frame would take about 35 ms a frame, below 30 fps. So the face runs on even frames and the pose on odd ones, and each reuses its last result (up to 150 ms old) in between; the camera held 30–35 fps.
    - **Without a face** the Kaggle model still works, at lower accuracy: the research measured about 90% on the restricted list without one. A missing or failing face or pose model turns that one off for the session, with one console warning, and the hands carry on.

167. **The model sees the movement plus context.**
    - `recognitionInput` keeps the last 6 s of tracked frames. The Kaggle model gets the segmenter's movement plus 5 frames each side.
    - ASL Citizen was trained on whole clips, hands at rest included, so it gets 15 frames before and 9 after. Nine is about all the camera has seen when the segmenter ends a movement. With that context its top-1 of 2731 on held-out signers rose from 47% to 55% (59% for whole clips).

168. **The decision.**
    - **Softmax over the ENABLED words only.** Accept at p ≥ 0.7.
    - **Open-set check (added after calibration).** The model must also rank the word first among ALL its 250 signs (ASL Citizen: within its top 3 of 2731). A sign outside the list still gets a big share of a softmax over a few dozen words, but the model's own top sign is then usually the real one. On held-out signers this cut out-of-vocabulary accepts from 12% to under 1% (Kaggle) and from 26% to 2% (ASL Citizen). It cost 3 points of recall (89% to 86%).
    - **Close calls.** Below 0.7, two words both at least 0.35 and within 0.25 of each other become the existing "Did you mean".
    - **The two models together.** A Kaggle accept wins. Otherwise ASL Citizen's top word is accepted if it is one the Kaggle model lacks, or the very word the Kaggle model ranked first without being sure. The two never overrule each other on a word both know.
    - All of this is in `engine/model/decide.ts`, which is pure and unit-tested.

169. **The vocabulary is one TS constant, `engine/model/vocabulary.ts`.** Each entry has the display word, its Kaggle label and its ASL Citizen glosses, and whether it is enabled.
    - **Display.** thankyou is "thank you", callonphone "call" and food "eat"; the rest are lower case. ASL Citizen's variants (MAIL1/MAIL2, WHAT1/WHAT2, EAT1/EAT2, CALL1/CALL2/PHONE) map to one word.
    - **On:** hello, thank you, yes, no, please, call, tomorrow, time, open, where, now, later, bad, water, eat, finish, wait, bye, see, look, listen, home, close, who, why, drink, happy, yesterday, night, sleep, think, like, dad, mom. With ASL Citizen installed, also help, more, email, mail, send, music, play, meeting, stop and what.
    - **Off:**
      - go: read as LATER 2 times in 12.
      - morning: known weak.
      - fine: with ASL Citizen on, it took 10 of the signs left out of the list.
      - good: GOOD and THANK YOU are nearly the same sign, and the Kaggle model read all 12 GOODs as THANK YOU.
    - **Untested extras.** look, night, sleep, think, like, dad and mom have no held-out clips. Enabling them changed the others' accuracy by under 1 point.
    - **Weak but harmless.** time (Kaggle 1/12) and listen (2/12) are mostly rejected rather than misread, so they stay on, and ASL Citizen rescues some of them.

171. **Recognition order for a movement: the model, then the taught signs, then the LLM.**
    - **The model.** A movement's outcome (the DTW result over the taught templates is computed as before) waits until the model answers, which takes a frame or two. Listening stays up meanwhile. An answer that doesn't come within 1.5 s of frame time (`MODEL_WAIT_MS`) is ignored.
    - **Combining it with the taught signs** (`withTaught`):
      - Both accept the same word: that word.
      - They accept different words: the more confident one wins. A taught match's confidence is `1 − 0.5 × distance / radius`: 1 at distance 0, 0.5 at the edge of the word's accept radius. It is compared with the model's p.
      - One accepts and the other is unsure or rejects: the one that accepts.
      - Both are unsure: one "Did you mean" with the model's options first.
      - The model rejects: the taught outcome as before. A rejection then goes to the guess-confirm-learn LLM path exactly as before (146).
    - **Letters, fingerspelling and Spell mode are untouched.** The model only sees movements, and Spell mode never asks it. A word the model names afterwards blocks the hand's resting shape as a letter, as a taught word does.
    - **Dictation** types a close call's best guess, as before.

172. **The model must not swallow control gestures.**
    - **Swipes.** A swipe made during a movement waits for the verdict, now also when nothing is taught (the model could name it). A model word takes the movement from the swipe only at p ≥ 0.9 (`GESTURE_OVERRIDE_P`). A taught word still always does (MUSIC, 158). Below that, the swipe acts as before.
    - **Holds.** The same 0.9 bar applies when the movement ends with the hand holding a control gesture's shape that is timing toward firing (fist, thumbs up, palm, finger count, shape; `GestureEngine.holding()`). A close call never takes a movement from a gesture.
    - **A gesture that fires while the model is still judging** (up to about 0.4 s with ASL Citizen) waits for its answer, like a swipe. A sure word wins, and TOMORROW's thumbs-up doesn't also end the phrase. Otherwise the gesture acts.
    - On held-out signers, 92% of correct Kaggle accepts are at least 0.9 sure.
    - **The real model on the synthetic gestures** (modelRecognition.test.ts):
      - a swipe gave bye 0.30, not the model's top sign (rank 5 of 250), so rejected;
      - a raised fist gave night 0.17, so rejected.

      The swipe still switched the mode and the fist still collapsed the card. Every existing engines test passes unchanged.

173. **The LLM is told the model's words.** Once the model has loaded, `store.modelWords` holds its enabled words in upper case ("THANK YOU", "CALL", "EAT"; ASL Citizen's only when installed). identifySign's `known` list is the taught words plus these. A guess then names a sign the way the model does, and a confirmed guess learns that label. The LLM path stays for words neither model knows: EMAIL, SEND, MUSIC and PLAY without ASL Citizen, SPOTIFY always.

174. **Settings › Teach a sign › Show me a sign asks the model first.** If the model accepts the movement or has a close call, its words are offered at once as "Is this THANK YOU?", with no LLM call, and a pick saves the repetition as before. Otherwise the LLM is asked as before. Teaching from the list is unchanged. It is optional now, for signs neither model knows.

## Conversational command mode

178. **Command mode is now a conversation with the agent.** Live testing: after signing HELLO the card stopped on the Sentence card ("Sentence / Hello", a pencil, "swipe ← delete · swipe → continue"). The user wanted the Droid agent's answer instead, and signing that keeps going rather than pausing after one sign. Now, in Command mode:
    - signing builds the phrase on the Building card for as long as the user signs;
    - lowering both hands sends it at once: the interpreter, then the agent, with nothing to approve in between;
    - one card shows the exchange: what the user signed, the agent's live steps, then its reply;
    - the next sign starts the next message, to the same persistent Droid session.

    Dictation and Spell mode are unchanged. So are the recognition code and its thresholds.

179. **Signing builds the phrase until both hands go down.** The first sign still shows Recognizing, and the next ones the Building card (tokens and the assembled sentence). Nothing ends the phrase but hands down (`handsDown`, about 1.2 s with no hands), a thumbs up, a swipe right or the ">" button; those used to open the Sentence card and now send. Thumbs up stays because TESTING (pretrained model, 14) relies on it, and a sign that ends in a thumbs up (TOMORROW) already wins over it (172). The Building card has a new hint, "hands down to send · swipe ← delete", and its ">" button is labelled "Send".

180. **Phrase end sends at once (`controller.sendPhrase`).**
    - The card switches to the conversation card in its `understanding` phase, with the assembled sentence and one step, "Understanding". The interpreter call is the old prefetch, renamed `interpretPhrase`: the same request, status line ("Rate limited, retrying..."), abort and cancel in main.
    - When it answers, the agent gets `intent = interpretation.intent ?? interpretation.sentence` and `sentence = interpretation.sentence`. A quick-menu pick with no intent from the interpreter becomes `"<pick>: <sentence>"`, as before.
    - **An interpreter that fails** (no key, a rate limit, a timeout, a crashed bridge) shows its error as the notice, and the assembled sentence goes to the agent anyway.
    - **A low-confidence reading** (below 0.6) is not asked about. Its intent may be a wrong guess, so the assembled sentence goes instead, for both `intent` and `sentence`. There is no Did you mean for intents any more. Sign-level Did you mean (`sign`, `learn`) stays.
    - New gesture › Sign a new task takes the same path and ends in the shape recording, not the agent.

Before, the card said "Nothing was done". The prompt still forbids such claims (185), and the title of anything that ran still comes only from tools.

184. **The reply is the Droid result's `text`, carried as `AgentResult.reply`.**
    - `AgentService.conclude` passes `result.text` (the SDK's final assistant message) only when the turn ended in `success`. `summarize` drops it after a decline, a stop or an error, where it could describe something that didn't happen.

185. **Agent prompt (`SYSTEM_PROMPT`).**
    - **New rule:** conversational messages (greetings, thanks, small talk, questions about the agent, the date or the time) get a brief, friendly reply of one or two plain-English sentences with no tool calls. Tasks use the fastasl tools as before.
    - **Also new:** it is one ongoing conversation, and replies are plain text (no Markdown, lists or emoji).
    - **Changed:** "Ask nothing" now applies to tasks. The turn's last line is `Message:` instead of `Task:`, because a greeting isn't a task.
    - **Kept word for word:** every safety rule (fastasl tools only; no files, shell or web; confirmation cards; contacts_find before sending; never claim what no tool result says; stop when a tool fails or is cancelled).

## Tracking the signer in a busy room

198. **The trackers now keep the person closest to the camera.** Live MEETING attempts in a crowded hackathon hall were read as "later" or "close" by ASL Citizen, with MEETING ranked #1,000–2,400 of 2,731, and then guessed as BALL by the LLM. Replaying the recorded attempts showed why:

## Streaming dictionary signs (ported from asl-dictionary-chat)

200. **Words now stream while the hands still move.** Ported from the teammate's `asl-dictionary-chat` branch (Yuvraajb, commit 220f562): `LexiconMatcher` (`engine/recognition/lexicon.ts`), the sign dictionary (`shared/dictionary.ts` + `dictionary.json`: HELLO, two-handed MEETING), `numbers.ts` (ASL 1–5) and their tests. Not ported: the chat view and service, the Sentence card's send-to-chat, Supabase sync and push-to-listen (conversation mode already sends signed phrases to the agent).
    - **`StreamingSignMatcher`** (`streaming.ts`) runs every frame outside Spell mode: the dictionary signs first, then each rule in `streamRules/index.ts` (`STREAM_RULES`, the `StreamRule` plugin interface in `streamRules/types.ts`). The first to fire wins. Rules get the last ≤1.5 s of frames since the last word, plus `{ aspect, face }`.
    - **A phrase streams word by word.** After a word, any other word may fire 300 ms later (`STREAM_GAP_MS`) and the same word 900 ms later (`STREAM_COOLDOWN_MS`). The dictionary's own cooldown is per sign, so MEETING can follow HELLO at once.
    - **The face box comes from FaceLandmarker** (`faceBox.ts`: the bounding box of the 468 mesh points), which the camera already runs. No second detector. It is reused for 1 s on frames without one. The face is now tracked wherever signs are taken outside Spell mode, not only once the sign model has loaded (`engines.ts`).
201. **Recognition order: streaming signs, then the sign model and taught signs, then the Gemini guess.** A streamed word is a `token` with `streamed: true` (`session.ts`). The movement it fired in, and any movement starting within 500 ms of it (`SETTLE_MS`), is *claimed*: it ends with no outcome, so it reaches neither the model, the taught templates nor a guess. A streamed word that arrives while the model still judges an earlier movement waits for that word, so the phrase keeps its order (`recognitionInput.ts`).
202. **Control gestures stay safe.**
    - No streaming word fires while a control gesture's hold is timing toward firing (`setStreamGate`, the gesture engine's `holding()`).
    - Swipes made while a dictionary sign's start is in view (`signPending`) wait for the movement's verdict, as they do for the model. A streamed word drops a held swipe.
    - A streamed word spends the shape it ends in (thumbs up, fist), as any recognized word does.
    - `streamEval.ts` builds synthetic clips of every control gesture (fist, open palm, five, 1–4, thumbs up, peace; raised to chest, chin, beside the face; swipes left, right, up), and `streaming.test.ts` checks that no dictionary sign or stream rule fires on them. One known clash is listed there: DAD fires on an open palm raised beside the forehead.
203. **HELLO and MEETING retuned on real signers.** Measured with the app's own MediaPipe tasks run on 895 ASL Citizen videos, and on 2,168 ASL Citizen Holistic clips (`live-bin`).
    - **HELLO.** Changes:
      - the forehead region is measured against the mesh face box;
      - a slow glide from the forehead keeps its start;
      - a start held still more than 0.6 s (a held hand, not a salute) can't fire it;
      - a swipe-fast straight stroke is left to the swipe;
      - at least 20% of the travel must be sideways, so lowering a hand is no HELLO.

      Recall went from 14% / 13% to 43% / 52%, with false fires on other words 1.7% / 1.5% (mostly FATHER) and none on the control clips.
    - **MEETING.** The flat O is now measured as the thumb tip close to the fingertips (`pinchMax`), since MediaPipe reads a flat O's fingers as straight. The hands must start open (`pinchMin`) and close by 0.6 hand lengths. Recall went from 8% / 24% to 75% / 90%, with false fires 0.2% / 1.4% (OPEN, MAIL, MORE).

Without that gate, an open hand, a raised index or a V held a quarter of a second would add "5", "1" or "2" to the phrase. In Ready the 2 is also the peace-sign screenshot. `setNumbers(on, allow)` keeps them ready for a later opt-in.

## Streaming FRIEND

216. **FRIEND streams, for the demo's "CALL FRIEND" and "EMAIL FRIEND"** (`streamRules/friend.ts`). The sign: both hands in X; the dominant index hooks over the other, the hands flip, and they hook again the other way round. On 29 ASL Citizen signers, the 2D landmarks show this as: the two index fingers touch, come apart while both hands move around each other (one rises as the other drops), and touch again. The flip itself is a turn in depth that the image barely shows. The rule fires the moment the second hook closes, when within 1.5 s all of these hold:
    - **Two hooks with a release between.** The closest points of the two index fingers (PIP, DIP, tip) come within 0.3 hand lengths. Then they are at least 0.5 apart, and at least 0.4 further apart than at the first hook. Then they are within 0.3 again, at most 700 ms after the widest point. At both hooks the palms are within 3 hand lengths.
    - **Both hands move.** After the first hook lets go, each palm moves at least 0.12 hand lengths. TIME's base hand holds still.
    - **The fingers point at each other at the hooks.** For each hand, take the cosine between the index (knuckle to tip) and the direction of the other palm. The median of the smaller of the two must be at least 0.1. Two index fingers held up side by side and tapped together point past each other.
    - **Both hands are index-only** (`indexOnly` in twoHandSigns.ts) in at least half the frames after the first hook lets go. That means index extension of at least 0.35 (a hook reads as half bent), the middle finger at most 0.5, and ring and pinky at most 0.5 on average. A tight hook often reads as a folded index, so the first hook's own frames aren't counted.
    - Which hand is which comes from position, never from the handedness label, so left-handed signers work too.

    So nothing static fires it, nor one hand, nor fists, flat hands, H hands (NAME) or MEETING's flat O.
    - **Order.** `STREAM_RULES` runs the face rules, then FRIEND, then the other two-handed rules, so FRIEND comes before TIME.
    - **Model vocabulary.** It now has `friend` (ASL Citizen gloss FRIEND), so the slower model path knows the sign too once ASL Citizen is installed.

217. **TIME no longer fires on FRIEND.** The user signed FRIEND live and got "time": a hooked index meeting the other hand passes for TIME's tap. TIME fires on the first hook, before FRIEND's second, so putting FRIEND first was not enough on its own. TIME now also needs:
    - a base hand that is index-only in at most half its frames (`baseIndex`), since TIME's base is a fist or a flat hand;
    - a tap that does not land index to index (within 0.4 hand lengths of the base's index in the last 3 frames) while the base holds its index out over the last 300 ms (`hook`, `hookFrames`, `hookMs`).

    Effect on TIME (twoHandSigns.eval.test.ts):
    - **Recall** is unchanged on the re-tracked clips (8/12) and on citizen-bin (10/12). On the Holistic `live-bin` clips it lost 1 of 18 (now 11/18): a signer whose base reads as index-out and whose tap lands on that index.
    - **False fires** went from 50 to 39 of 3,151 other clips.
    - **FRIEND clips** went from 8 of 58 firing TIME to 2 of 58. In both remaining clips the base's X reads as a fist or an open hand.
